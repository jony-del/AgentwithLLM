### 面试时最重要的边界

- ReAct 是当前项目的核心运行方式。
- CoT 的推理能力主要来自底层大模型，项目负责接入和状态管理。
- Plan-and-Execute 是工程化变体，并非完全分离的双模型架构。
- 长期记忆已形成“召回—使用—抽取—巩固”闭环，当前默认使用本地 Exact、BM25、BGE-M3 Dense、RRF 和 BGE Reranker 混合检索。
- 多智能体已经实现，但必须通过评估证明它优于单智能体。
- 项目有评估基础设施，但还没有完整的业务任务基准平台。
- PyTorch、LangChain、AutoGen 和强化学习不能描述成当前项目已经使用。

## 2. 项目定位与一句话介绍

### 项目定位

Polaris 是一个使用 Python 自主实现的 ReAct 智能体运行系统，主要面向代码仓库操作和需要真实工具执行的复杂任务。

它解决的不是“如何让模型调用一次函数”，而是：

- 如何让模型持续观察环境并调整行动；
- 如何让复杂任务能够规划、执行、纠错和结束；
- 如何安全地读写文件、执行命令和访问网络；
- 如何在上下文变长后保持任务连续性；
- 如何让多个智能体并行协作又不失控；
- 如何恢复会话、审计轨迹和分析失败；
- 如何把智能体从演示程序变成可部署产品。

### 一句话介绍

> Polaris 是我自主实现的 Python ReAct 智能体运行系统，它围绕大模型补齐了任务规划、工具编排、长短期记忆、多智能体协作、权限沙箱、上下文压缩、会话恢复和运行审计，使智能体能够安全、持续、可观测地完成真实任务。

### 项目最值得强调的四个特点

1. **完整性**
   - 从用户输入一直覆盖到最终结果、日志、记忆和会话恢复。

2. **安全性**
   - 不只依赖模型判断，还设置确定性权限、敏感路径保护和操作系统沙箱。

3. **长期运行能力**
   - 支持上下文压缩、超时、取消、后台任务、重试和故障恢复。

4. **工程可控性**
   - 每个关键判断都有明确边界、运行记录和测试。

## 3. 系统总体架构

<a id="section-3-layers"></a>

系统可以分成七层。

| 层级 | 主要职责 |
|---|---|
| 交互层 | 接收一次性任务或连续对话，展示流式结果、工具状态和权限询问 |
| 配置层 | 合并默认配置、用户配置、项目配置、环境变量和命令行参数 |
| 模型层 | 适配不同大模型协议，处理流式输出、推理状态、重试和令牌统计 |
| 智能体层 | 执行 ReAct 循环，维护任务状态，决定是否继续、压缩或结束 |
| 工具层 | 提供文件、命令、网络、代码理解、计划、记忆和多智能体能力 |
| 安全层 | 执行参数检查、权限判断、敏感路径保护、网络策略和沙箱隔离 |
| 状态与观测层 | 保存会话、长期记忆、任务轨迹、工具结果和运行指标 |

### 核心数据流

用户请求  
→ 加载历史、项目上下文和相关记忆  
→ 模型理解目标并产生回答或工具行动  
→ 安全系统判断工具是否允许执行  
→ 工具执行并返回真实环境结果  
→ 结果加入当前上下文  
→ 模型根据新结果重新决策  
→ 没有后续工具行动时生成最终答案  
→ 保存日志和会话；启用记忆且自然结束时增量抽取长期记忆

### 横向能力

- 上下文压缩贯穿整个运行过程。
- 权限和沙箱覆盖所有有副作用的操作。
- 运行日志覆盖模型、工具、权限、压缩和子智能体事件。
- 并发与限流同时约束工具调用和模型请求。
- 会话状态支持恢复、继续和分叉。

## 4. 用户请求的完整运行流程

<a id="section-4-1"></a>

### 4.1 系统启动

系统启动时完成以下装配：

1. 读取环境变量和配置文件。
2. 确定模型服务、模型名称和推理参数。
3. 创建交互界面或无界面运行方式。
4. 建立工具注册表。
5. 根据当前环境隐藏不可用工具。
6. 连接外部工具协议服务。
7. 创建会话、任务状态和运行编号。
8. 准备沙箱和权限策略。
9. 加载技能、生命周期扩展和插件。
10. 解析长期记忆配置；框架内置默认关闭，当前项目配置开启，环境变量和命令行可覆盖启用状态。
11. 为所有模型调用设置共享并发上限和请求速率。

### 启动阶段的关键判断

- 如果命令执行工具在本机不可用，则不向模型暴露。
- 如果没有外部工具连接，则不暴露相关资源工具。
- 如果没有配置代码语言服务，则不暴露代码理解工具。
- 如果无人值守模式没有可用沙箱，默认拒绝启动。
- 如果某个工具被管理员策略完全禁止，则从工具列表移除。
- 如果没有任何可用技能，则不暴露技能调用入口。

<a id="section-4-2"></a>

### 4.2 请求进入

一条新请求进入后，系统按以下顺序构建上下文：

1. 创建系统行为说明。
2. 加入用户当前请求。
3. 根据用户请求对主题记忆执行 Exact、BM25、Dense、RRF 和重排序。
4. 只注入预算内命中的完整历史片段；没有合格结果时不注入记忆块。
5. 读取项目级说明。
6. 读取当前分支、工作区状态和最近提交等项目上下文。
7. 如果是连续会话，则插入此前对话历史。
8. 同步当前权限模式和计划模式状态。
9. 触发用户输入检查。
10. 输入检查可以拒绝、改写或补充上下文。

### 上下文的优先级原则

- 系统安全规则优先于项目说明。
- 项目文件和工具输出都属于不可信环境信息。
- 长期记忆以“不可信、可能过期的历史信息”注入，不能授权、修改系统规则或覆盖当前用户明确要求；涉及当前文件、配置和运行状态的内容必须重新验证。
- 历史消息不能反复叠加系统提示和项目上下文。
- 当前任务必须位于模型能够清楚识别的位置。

<a id="section-4-3"></a>

### 4.3 ReAct 循环

每一轮按以下逻辑运行：

1. 检查用户是否中断任务。
2. 检查是否达到最大运行时间。
3. 检查是否达到可选的最大轮数。
4. 如果即将超时，提醒模型停止扩展并尽快总结。
5. 判断上下文是否接近模型窗口上限。
6. 如有需要，先压缩旧上下文。
7. 把当前消息和可用工具描述发送给模型。
8. 接收模型回答、推理状态、工具行动和令牌统计。
9. 保存本轮模型输出和运行指标。
10. 判断模型是否请求工具。

如果模型没有请求工具：

- 执行停止阶段检查；
- 停止阶段可以要求模型继续补充；
- 连续要求继续的次数有上限；
- 最终确认结束后返回答案。

如果模型请求工具：

- 进入工具执行流程；
- 将工具结果作为环境观察写回上下文；
- 开始下一轮模型决策。

### 自然结束条件

任务主要通过“模型不再请求工具”自然结束。

最大轮数和最大运行时间不是主要完成条件，而是防止无限循环的安全边界。

<a id="section-4-4"></a>

### 4.4 工具执行

每个工具行动依次经过：

1. **前置扩展检查**
   - 可以改写参数、补充信息或拒绝执行。

2. **工具存在性检查**
   - 未知工具不会让系统崩溃，而是返回可理解的失败结果。

3. **参数结构检查**
   - 参数必须满足工具声明的数据结构。

4. **权限判断**
   - 检查管理员策略、明确拒绝规则、当前模式、敏感路径、网络策略和工具风险。

5. **人工或自动审批**
   - 只有剩余的可审批动作才可能进入自动分类或人工询问。

6. **资源冲突分析**
   - 判断多个工具是否会读写同一文件、同一任务或同一共享状态。

7. **并发分组**
   - 无冲突操作可以并行；
   - 有冲突操作按顺序执行；
   - 未声明资源边界的工具保守地独占执行。

8. **真实执行**
   - 阻塞型工具放入工作线程；
   - 原生异步工具直接在事件循环中执行。

9. **结果处理**
   - 截断过长输出；
   - 保存完整输出引用；
   - 执行后置扩展；
   - 写入审计日志。

10. **结果回注**
    - 成功或失败都会作为环境观察返回给模型。

### 为什么工具失败不直接终止任务

工具失败本身也是有价值的信息。

模型看到失败原因后可以：

- 修正参数；
- 改用其他工具；
- 缩小操作范围；
- 重新规划；
- 请求用户补充信息；
- 返回部分结果并说明阻塞。

<a id="section-4-5"></a>

### 4.5 任务结束

任务完成时执行：

1. 输出最终答案。
2. 统计运行时间。
3. 统计 ReAct 轮数。
4. 统计各工具调用次数。
5. 统计输入、输出和上下文令牌。
6. 写入最终运行事件。
7. 保存完整会话链。
8. 从对话中提取值得跨会话保留的信息。
9. 关闭后台扩展任务和日志句柄。

### 异常结束

| 异常 | 处理逻辑 |
|---|---|
| 用户中断 | 在模型流式阶段和工具轮次安全点停止 |
| 达到时间上限 | 先提醒收尾，再执行硬停止 |
| 工具异常 | 转换为失败观察，由模型决定后续行动 |
| 模型请求过大 | 启动上下文恢复流程 |
| 子智能体异常 | 隔离为子任务失败，不拖垮其他子任务 |
| 记忆抽取异常 | 不影响已经完成的主任务 |
| 观察型扩展异常 | 记录并降级，不应破坏主任务 |
| 安全型扩展异常 | 可以按配置拒绝继续 |

## 5. ReAct 原理与项目实现

### ReAct 的核心思想

ReAct 让模型在推理和行动之间反复切换：

目标理解  
→ 判断下一步  
→ 调用工具  
→ 获得真实结果  
→ 根据结果修正判断  
→ 继续行动或结束

项目选择 ReAct 不是因为它比其他架构更“高级”，而是因为代码 Agent 的核心场景同时具有三个特征：

1. **执行路径不确定**
   - 在读取仓库、日志和测试结果前，无法提前枚举全部步骤。
2. **工具之间存在依赖**
   - 后一个动作的参数和目标通常取决于前一个动作的真实输出。
3. **执行过程中持续获得新信息**
   - 新文件、诊断或失败测试可能推翻原有假设，要求立即改线。

### 为什么代码 Agent 需要 ReAct 闭环

以“修复一个 Bug”为例，模型开始时通常并不知道根因在哪里：

```text
搜索代码
→ 读取候选文件和调用链
→ 根据证据形成假设
→ 修改代码
→ 运行测试
→ 根据成功或新报错决定结束、继续定位或回滚调整
```

这条链路不是固定流水线。搜索可能表明应该读取另一模块，文件内容可能推翻最初判断，测试失败又会产生新的定位线索。因此每一步都可能改变后续路径：

```text
搜索代码 → 读取文件 → 修改代码 → 运行测试
    ↑          ↑          ↑          │
    └──────────每一步都可能根据真实结果重新决策──┘
```

在 Polaris 中，模型每轮既可以直接回答，也可以生成结构化工具调用；文件内容、命令输出、测试结果和工具错误都会作为 Observation 返回模型。失败不是简单的流程异常，而是下一轮决策所需的环境证据。

### 与其他架构的选型比较

| 方案 | 优势与适用场景 | 不作为代码任务默认主循环的原因 | 在 Polaris 中的角色 |
|---|---|---|---|
| 固定 Workflow / DAG | 确定性强、容易测试；适合“查订单—验库存—生成退款单”等稳定流程 | 不同仓库、Bug 和测试结果会产生大量事前无法枚举的分支 | 承担参数校验、权限、沙箱、审计、生命周期等必须确定的治理环节 |
| 纯 Plan-and-Execute | 适合目标清晰、步骤相对稳定的长任务 | 初始计划基于不完整信息，读取新代码或测试失败后容易失效；频繁全量重规划会增加成本和延迟 | 以动态任务清单和严格只读的 Plan 模式补充 ReAct |
| Reflection | 可以让模型对结果再检查一次 | 模型自我评价并不稳定，每轮反思还会增加 Token 和延迟 | 优先用测试、诊断和真实文件等外部证据验证；必要时才增加反思 |
| 默认多 Agent | 可并行处理真正独立的子问题 | 会复制上下文、增加通信和模型成本，并带来资源与文件冲突 | 只在边界清晰、收益明确、可独立交付的子任务中启用 |

因此，架构选择的关键不是“哪个范式最好”，而是把开放式决策交给 ReAct，把确定性强、可预先编码的约束交给 Workflow，再按风险和任务结构引入计划或多智能体。

### Polaris 不是“裸 ReAct”，而是混合架构

Polaris 以 ReAct 作为动态决策主循环，同时组合三类补充机制：

- **ReAct**：根据环境变化决定下一步做什么；
- **Plan**：分解复杂目标，并让高风险任务先只读调查、经人工确认后再执行；
- **确定性 Workflow**：负责 Schema、权限、沙箱、审计、状态更新和生命周期；
- **多 Agent**：负责可以独立并行、交付物明确的子任务。

模型决策和执行治理必须分开：

```text
非确定性的模型决策：
搜索代码 → 读取文件 → 修改代码 → 运行测试

确定性的执行治理：
参数校验 → 权限判断 → 用户确认 → 沙箱执行
        → 结果审计 → 状态更新 → 资源清理
```

模型决定“下一步做什么”，运行时决定“怎样调度和恢复”，安全系统决定“是否允许执行”。这三个决策层分离后，模型即使判断错误，也不会自动绕过系统的硬安全边界。

### 项目中的对应关系

| ReAct 概念 | 项目中的含义 |
|---|---|
| 推理 | 模型基于目标、历史和环境结果判断下一步 |
| 行动 | 模型选择某个工具并给出参数 |
| 行动空间 | 当前向模型开放的全部工具能力 |
| 环境观察 | 文件、命令、网络、测试或子智能体返回的结果 |
| 状态 | 当前消息、任务清单、计划、会话和记忆 |
| 结束 | 模型不再请求工具并给出最终回答 |

### 为什么项目使用结构化工具调用

没有依赖固定的“思考、行动、观察”文本格式，而是使用模型原生结构化工具调用。

好处：

- 不需要脆弱的文本解析；
- 工具名称和参数更明确；
- 参数可以自动检查；
- 不同模型服务更容易统一；
- 日志和评估更容易结构化。

### ReAct 的优势

- 适合开放式任务；
- 可以根据环境反馈改变路线；
- 工具失败后能够恢复；
- 不要求提前知道完整执行步骤；
- 能够把复杂任务分解为多个连续决策。

### ReAct 的问题

- 可能反复调用同一个工具；
- 可能走弯路；
- 每一轮都需要模型请求，成本较高；
- 上下文会持续增长；
- 模型可能过早结束或长期不结束；
- 模型可能生成高风险操作。

### 项目的应对方式

- 任务清单用于保持目标；
- 计划模式用于高风险任务；
- 运行时间和轮数限制防止失控；
- 用户取消、停止阶段继续次数和上下文恢复次数都设置上限；
- 上下文压缩控制窗口；
- 工具失败作为观察反馈；
- Schema 校验、权限管线和沙箱限制工具风险；
- 资源冲突分析让无冲突工具安全并行；
- 运行轨迹用于事后分析；
- 停止阶段检查防止过早结束。

## 6. CoT 与复杂推理

### CoT 的含义

CoT 指模型通过中间推理步骤解决复杂问题。

在当前项目中，复杂推理主要由底层大模型完成，项目负责：

- 配置推理强度和预算；
- 接收流式推理信息；
- 保存跨工具轮所需的推理状态；
- 保证不同模型协议的状态能够正确续接；
- 将最终推理结果与工具行动结合。

### 项目没有做什么

- 没有训练自己的推理模型；
- 没有把长篇思维过程当作正确性指标；
- 没有依赖公开完整思维链判断任务是否完成；
- 没有把模型推理能力包装成自研推理算法。

### 面试中如何表达

> 当前项目完成的是模型推理能力的工程接入和状态管理。复杂推理主体来自底层模型，系统负责给模型提供正确上下文、工具反馈和运行边界，并通过最终任务结果、测试和工具证据判断是否正确。

### CoT 与 ReAct 的区别

| 对比项 | CoT | ReAct |
|---|---|---|
| 核心 | 内部推理链 | 推理与外部行动交替 |
| 信息来源 | 已有上下文 | 已有上下文加真实环境反馈 |
| 是否调用工具 | 不一定 | 通常会 |
| 适用任务 | 数学、逻辑、分析 | 搜索、代码、操作和开放任务 |
| 当前项目角色 | 模型推理能力 | 系统主运行方式 |

## 7. Plan-and-Execute 与自主规划

### Plan-and-Execute 的基本逻辑

任务理解  
→ 生成计划  
→ 执行计划步骤  
→ 检查结果  
→ 必要时重新规划  
→ 完成任务

### 项目的三层规划

#### 第一层：动态任务清单

适合普通多步任务。

- 模型创建完整任务清单；
- 每次只保持一个步骤进行中；
- 完成后更新状态；
- 环境结果变化时可以修改后续计划。

特点：

- 轻量；
- 与 ReAct 循环结合；
- 计划可以动态变化；
- 不需要额外审批。

#### 第二层：显式计划模式

适合修改范围大、风险高或用户要求先设计后实施的任务。

流程：

进入计划模式  
→ 系统切换为严格只读  
→ 调查代码和环境  
→ 对关键不确定项询问用户  
→ 形成完整计划  
→ 保存为独立计划文档  
→ 请求用户批准  
→ 恢复原权限模式  
→ 按批准计划执行

核心价值：

- 分离“调查设计”和“真实修改”；
- 计划可以被用户审阅；
- 防止模型边想边改；
- 可以在批准时申请有限范围的操作权限。

#### 第三层：多智能体任务拆分

适合可以并行的复杂任务。

流程：

创建团队  
→ 创建多个子任务  
→ 指定负责人  
→ 启动不同角色的智能体  
→ 子智能体更新进度并发送结果  
→ 主智能体汇总任务状态  
→ 处理冲突和未完成项  
→ 生成最终结论

### 当前实现的准确边界

当前系统是工程化的 Plan-and-Execute 变体：

- 有独立计划状态；
- 有只读调查阶段；
- 有计划文档；
- 有人工审批；
- 有动态重新规划；
- 有团队任务拆分。

但规划与执行仍由同一个 ReAct 运行系统驱动，不是完全独立的规划模型和执行模型。

### 什么时候应先规划

- 涉及多个模块；
- 修改风险较高；
- 存在多个可选方案；
- 需求存在关键歧义；
- 需要用户批准；
- 任务可以拆成独立子任务；
- 预计需要大量工具调用。

### 什么时候不需要计划

- 单一明确问题；
- 一次读取即可回答；
- 很小的局部修改；
- 确定性单工具任务；
- 规划成本高于执行成本。

## 8. 意图理解与动态决策

### 当前意图理解方式

项目没有单独的意图分类模型。

大模型综合以下信息理解用户目标：

- 当前请求；
- 历史对话；
- 项目说明；
- 相关长期记忆；
- 当前权限模式；
- 可用工具及其用途；
- 可用技能和插件；
- 前面工具返回的真实结果。

### 优点

- 支持开放域任务；
- 不需要预先枚举所有意图；
- 新增工具后可以自然扩展能力；
- 能理解组合意图和复杂自然语言。

### 缺点

- 每次都依赖大模型，成本较高；
- 高频简单任务缺少稳定路由；
- 意图结果没有独立结构化记录；
- 业务统计和策略控制不够直接。

### 面向业务的升级方案

建议增加分层意图路由：

| 任务类型 | 推荐处理 |
|---|---|
| 简单问答 | 直接回答 |
| 固定单工具任务 | 确定性流程 |
| 普通开放任务 | ReAct |
| 高风险写操作 | 先计划再审批 |
| 大型可拆分任务 | 多智能体 |
| 信息不足任务 | 先向用户提问 |

### 动态决策的三个层面

#### 模型决策

- 是否需要工具；
- 选择哪个工具；
- 工具参数是什么；
- 是否需要重新规划；
- 是否已经可以结束。

#### 运行时决策

- 哪些工具当前可用；
- 哪些调用可以并行；
- 是否需要压缩；
- 是否需要重试；
- 是否需要委派子智能体；
- 是否即将超时。

#### 安全决策

- 操作是否允许；
- 是否需要人工确认；
- 是否必须进入沙箱；
- 是否触及敏感路径；
- 网络目标是否允许；
- 子智能体权限是否超过父智能体。

### 面试总结

> 智能体的动态决策不是单一模型输出，而是模型策略、运行时调度和安全策略共同作用的结果。

## 9. 工具调用系统

### 工具系统解决的问题

模型本身只能生成文本。工具系统让模型能够：

- 读取真实文件；
- 搜索代码；
- 修改内容；
- 执行测试；
- 运行命令；
- 查询网络；
- 操作笔记本；
- 使用代码语言服务；
- 创建计划；
- 启动子智能体；
- 连接外部业务系统。

### 工具调用完整生命周期

工具发现  
→ 模型选择工具  
→ 参数结构检查  
→ 权限检查  
→ 资源冲突判断  
→ 沙箱准备  
→ 工具执行  
→ 输出限制和脱敏  
→ 记录日志  
→ 结果返回模型

### 工具分类

| 类别 | 能力 |
|---|---|
| 文件与搜索 | 浏览目录、查找文件、搜索文本、读取文件、查看差异 |
| 编辑 | 单点编辑、多点编辑、补丁修改、写入文件 |
| 命令与测试 | 运行命令、执行测试、管理后台任务 |
| 计划 | 维护任务清单、进入计划模式、保存计划、批准计划 |
| 网络 | 搜索网页、抓取网页 |
| 代码理解 | 定义、引用、符号、诊断等语言服务能力 |
| 长期记忆 | 检索、显式写入、可恢复遗忘 |
| 多智能体 | 委派子任务、建立团队、分配任务和通信 |
| 扩展能力 | 外部工具协议、技能、插件、定时任务 |

<a id="tool-list-scope"></a>

### 工具清单口径

这里的“工具”特指**模型可以通过结构化 Tool Call 调用的能力**，不把以下概念重复算入：

- Slash Command 或 CLI 子命令，例如 `/permissions`、`/mcp`、`polaris health`；
- Hook 本身；Hook 是工具调用前后的确定性扩展点；
- 某个具体 Skill 的说明正文；多个 Skill 都通过一个 `Skill` / `skill` 工具执行；
- MCP Resource 和 MCP Prompt；它们分别是资源与命令，不等于 MCP Tool；
- `bash` 或 `powershell` 内能够启动的 `git`、`pytest`、`npm` 等外部程序；它们是 Shell 工具的参数，不是新的模型工具名。

“所有工具”还必须区分五种状态：

| 状态 | 含义 |
|---|---|
| 内置常驻 | 运行时注册后通常直接把 Schema 发给模型 |
| 条件内置 | 代码中存在，但依赖包、平台、会话形态或配置不满足时不注册或被移除 |
| 延迟工具 | 只保留名称和描述，`tool_search` 命中后才实例化并在后续轮次暴露 Schema |
| 内部专用 | 只注入特定子 Agent / 团队成员，不提供给主 Agent |
| 动态扩展 | 由 MCP 服务器或插件在启动、重载时提供，数量没有固定上限 |

因此，不能只看某个工具类是否存在，也不能用一个固定数字描述所有机器、所有权限模式和所有会话。下列清单的核验日期为 **2026-07-31**。

| MCP Resource | `read_mcp_resource` | 延迟、条件保留 | 读取指定 MCP Resource |
| 队员内部通信 | `team_inbox_read` | 仅队员注入 | 读取队员自己的 Inbox 并推进未读游标 |
| 队员内部通信 | `team_message_send` | 仅队员注入 | 使用文件锁向另一个队员 Inbox 发送消息 |

需要特别注意：

- `web_fetch` / `web_search` 只有安装 `[web]` 依赖时才通过 `_web_tool` 注册；当前 `.venv` 已满足依赖，所以 47 个目录工具包含它们，否则目录固定工具会降为 45 个。
- 10 个延迟工具是：`config`、`cron_create`、`cron_list`、`cron_delete`、`enter_worktree`、`exit_worktree`、`list_mcp_resources`、`read_mcp_resource`、`lsp`、`notebook_edit`。
- `write_plan` / `exit_plan` 虽然存在于活动注册表，但通过工具级权限只允许在 Plan Mode 正确阶段操作 Agent 自有计划文件。
- `task_output` / `task_stop` 管理的是 Shell 后台进程；团队任务则由 `task_create` / `task_get` / `task_list` / `task_update` 管理，两者名称接近但状态存储不同。

<a id="polaris-mcp-tool-list"></a>

### 当前项目配置的 MCP 工具

Polaris 的 `MCPAdapter` 会把外部工具注册为 **`<server>__<tool>`**，避免服务器之间重名。插件携带的 MCP 也走同一适配路径。与固定目录工具不同，这部分必须连接服务器后才能知道准确清单。

对当前 `agent.toml` 执行 `polaris mcp list`，`git`、`fetch`、`time` 三个服务器共返回 **15 个动态工具**：

| MCP 服务器 | 工具 | 当前服务器级风险 | 用途 |
|---|---|---|---|
| fetch | `fetch__fetch` | Read | 抓取 URL，可提取 Markdown |
| git | `git__git_add` | Write | 添加内容到暂存区 |
| git | `git__git_branch` | Write | 列出分支 |
| git | `git__git_checkout` | Write | 切换分支 |
| git | `git__git_commit` | Write | 创建提交 |
| git | `git__git_create_branch` | Write | 从可选基线创建分支 |
| git | `git__git_diff` | Write | 查看分支或提交之间差异 |
| git | `git__git_diff_staged` | Write | 查看已暂存修改 |
| git | `git__git_diff_unstaged` | Write | 查看工作区未暂存修改 |
| git | `git__git_log` | Write | 查看提交日志 |
| git | `git__git_reset` | Write | 取消暂存全部修改 |
| git | `git__git_show` | Write | 查看一个提交的内容 |
| git | `git__git_status` | Write | 查看工作树状态 |
| time | `time__convert_time` | Read | 在时区之间转换时间 |
| time | `time__get_current_time` | Read | 查询指定时区当前时间 |

这里能看出当前 MCP 风险是**服务器级粗粒度**：`git` 服务器配置为 `risk = "write"`，所以 `git__git_status`、`git__git_log` 等只读语义工具也继承 Write。框架原生 `git_diff` 则声明为 Read。后续若要减少不必要审批，应拆分 MCP 服务器风险或支持描述符级风险，而不是根据工具名称临时猜测。

按当前环境做集合统计：

- 47 个目录内置工具；
- 2 个团队成员内部工具；
- 15 个当前配置 MCP 工具；
- 合计是 **64 个已确认名称的项目工具能力并集**，但它们不会同时出现在同一个 Agent 的单轮上下文中；
- 后续安装插件或新增 MCP 服务器后，这个数字会动态增加。

<a id="tool-mapping"></a>

### Claude Code 与 Polaris 的工具映射

| 能力 | Claude Code | Polaris | 关键差异 |
|---|---|---|---|
| 读取 / 搜索 | `Read`、`Glob`、`Grep` | `read_text_file`、`list_dir`、`glob`、`search_text` | Polaris 额外保留目录列表工具，并显式提供 Ripgrep 失败后的 Python 回退 |
| 编辑 | `Edit`、`Write`、`NotebookEdit` | `edit_file`、`multi_edit`、`apply_patch`、`write_text_file`、`notebook_edit` | Polaris 把多编辑和统一 Diff 作为独立原生工具 |
| 命令 | `Bash`、`PowerShell` | `bash`、`powershell` | 两者都有命令解析、权限和后台执行；规则语法与沙箱实现不同 |
| 后台任务 | `Monitor`、`TaskOutput`、`TaskStop` | `task_output`、`task_stop` | Polaris 可管理后台进程，但没有与 `Monitor` 完全等价的逐行事件反应 / WebSocket 监控工具 |
| 测试 / Git | 主要通过 `Bash` | `run_tests`、`git_diff`，也可通过 Shell / MCP | Polaris 为 Pytest 与 Diff 提供更窄、更易审计的原生接口 |
| 计划 / 任务 | Plan、Task、`TodoWrite` 系列 | `enter_plan`、`write_plan`、`exit_plan`、`update_todos` 与 Team Task 系列 | Polaris 明确区分当前执行待办和团队共享任务 |
| 子 Agent | `Agent`、`SendMessage`、`Workflow` | `dispatch_agent`、`teammate_spawn`、团队消息工具 | Polaris 有两套协作模式，但没有独立的动态 `Workflow` 工具 |
| 定时 | Cron、`ScheduleWakeup`、`RemoteTrigger` | Cron 三工具 | Polaris 调度器只向仍然存在的 Agent 队列投递 Prompt，不创建 Agent，也不是 claude.ai Routine |
| Web | `WebSearch`、`WebFetch` | `web_search`、`web_fetch`，当前另有 `fetch__fetch` | Polaris 原生 Web 工具有 SSRF、重定向逐跳和域名策略；MCP Fetch 是另一条外部链路 |
| LSP | `LSP` | `lsp` | 都按语言服务器提供代码理解；Polaris 是延迟工具且依赖显式服务器配置 |
| Skill | `Skill` | `skill` | 都把工作流说明与真实执行工具分开 |
| MCP | MCP 动态工具、Resource 工具、`ToolSearch` | `<server>__<tool>`、Resource 工具、`tool_search` | Claude Code 默认延迟加载 MCP Schema；Polaris 当前把 MCP Tool 直接注册，只有 MCP Resource 两工具延迟 |
| 长期记忆 | 不是 Tools Reference 中的显式 CRUD 工具组 | `memory_search`、`memory_write`、`memory_forget` | Polaris 把长期记忆维护作为一等工具能力 |
| 产品 / 云能力 | `Artifact`、通知、Remote Routine、发送文件、Onboarding 分享、结构化 Findings | 无直接等价原生工具 | 这些是 Claude Code 产品服务能力，不应误写成通用 Coding Agent 必备内核 |
| Polaris 管理能力 | 无一一对应项 | `config`、`team_create`、`team_status`、`team_delete`、`echo` | Polaris 暴露更多本地 Runtime 管理和确定性诊断工具 |

核心结论不是“谁的工具数量更多”，而是两者分层方式不同：Claude Code 当前包含更多 claude.ai 产品与远程协作能力；Polaris 包含显式长期记忆、本地 TeamStore、专用测试 / Git 工具和更细的本地 Runtime 管理能力。

<a id="tool-availability"></a>

### 工具可用性与注册逻辑

Polaris 的实际工具面按以下顺序形成：

1. `catalog.discover()` 导入 `agent_core.tools` 全部模块，让 `@builtin_tool` 装饰器完成自注册。
2. `populate_registry()` 把常用工具放入活动表，把 `deferred = True` 的工具放入延迟表。
3. CLI 在构造 Agent 前连接 `agent.toml` 中已启用的 MCP 服务器，通过 `MCPAdapter` 把每个 `<server>__<tool>` 注册进活动表。
4. `ReActAgent.__init__` 绑定 Workspace、Session、Sandbox 和 Web Policy。
5. 运行时移除不可用能力：
   - Bash / PowerShell 被关闭或找不到合法解释器时移除；
   - 两种 Shell 都不可用时同时移除 `task_output` / `task_stop`；
   - 没有实时 UI / 提问回调时移除 `ask_user_question`；
   - 没有 MCP Manager 时移除两个 MCP Resource 工具；
   - 没有 LSP Server 时移除 `lsp`；
   - Scheduler 关闭时移除三个 Cron 工具；
   - 没有可持久化记忆 Repository 时移除三个 Memory 工具；
   - 没有模型可调用 Skill 时移除 `skill`；
   - 管理员整工具拒绝规则可在工具暴露前移除相应延迟工具。
6. 插件在构造尾部加载；插件 MCP Tool 可以注册。重载会先完整构建并校验新代，再在同步切换阶段替换旧代，构建失败时保留旧代。
7. 每次模型调用只使用 `registry.schemas_for_llm()` 中的**活动工具**。`tool_search` 命中延迟工具后调用 `activate()`，其完整 Schema 从下一次模型请求开始可见。
8. 普通子 Agent 和团队成员使用显式 Allow Set 重新构建自己的 Registry；子 Agent 不会继承 `dispatch_agent` / `skill` 等可递归扩张能力，团队成员才额外获得两个 Inbox 工具。

Claude Code 也存在类似的“列出不等于同时暴露”边界。官方文档说明：MCP Tool Search 默认只在启动时放入工具名称和服务器说明，需要时才加载完整 Schema；只读工具通常可以并行，修改状态的 `Edit`、`Write`、`Bash` 等顺序执行。Polaris 的差异是按工具声明的资源读写锁做冲突分波，比单纯按“只读 / 修改状态”再细一层。

### 延迟工具发现

不是所有工具都在每轮直接发送给模型。

原因：

- 工具越多，提示占用越大；
- 工具选择更容易混淆；
- 很多重型能力只在少数任务中使用；
- 某些工具依赖当前环境；
- 被禁止的能力不应暴露。

逻辑：

模型提出能力需求  
→ 工具搜索器检索可用能力  
→ 命中延迟工具  
→ 检查环境依赖  
→ 激活工具  
→ 后续轮次可直接使用

当前真正由 Polaris 目录标记为延迟的是 Config、Scheduler、Worktree、LSP、Notebook 和 MCP Resource 工具。**MCP 服务器提供的业务 Tool 当前由 `MCPAdapter` 直接注册，不经过 `tool_search` 延迟激活**；这一点与 Claude Code 默认延迟加载 MCP Tool 的行为不同。

### 参数检查

每个工具都有明确的参数结构。

执行前检查：

- 必填字段；
- 数据类型；
- 可选值范围；
- 字符和大小限制；
- 不允许的额外字段；
- 路径是否越过工作区。

### 工具输出管理

工具输出过长会：

- 增加上下文；
- 降低模型注意力；
- 触发窗口超限；
- 泄露不必要信息。

因此系统会：

- 限制最大行数；
- 限制最大字符数；
- 保留摘要或头尾；
- 将完整内容保存到文件；
- 给模型返回可再次读取的引用。

### 工具系统的面试亮点

- 工具不是简单函数集合，而是有契约、有权限、有并发语义、有观测的执行平台。
- 同一工具的风险由具体参数决定，不能只看工具名称。
- 工具失败仍进入 ReAct 反馈环。
- 工具集合会根据环境、权限和任务动态变化。

## 10. 短期记忆与上下文管理

### 短期记忆包含什么

| 状态 | 用途 |
|---|---|
| 当前消息历史 | 保存本次任务的交流和工具观察 |
| 任务清单 | 保存规划步骤和完成状态 |
| 计划状态 | 保存当前是否处于计划模式 |
| 最近读取文件 | 压缩后恢复关键代码上下文 |
| 后台进程状态 | 保存长时间命令及其输出 |
| 团队任务状态 | 保存多智能体协作进度 |
| 模型协议状态 | 保证跨工具轮推理能够续接 |
| 会话记录 | 支持退出后恢复 |

### 为什么不能无限保留历史

- 模型上下文窗口有限；
- 输入令牌成本不断增加；
- 延迟持续上升；
- 旧信息可能干扰当前任务；
- 工具描述和项目上下文本身也占空间。

### 主动压缩逻辑

每轮调用模型前：

1. 读取最近一次模型返回的真实令牌使用量。
2. 估算此后新增消息的令牌。
3. 判断是否接近有效上下文阈值。
4. 如果未达到阈值，保持原上下文。
5. 如果达到阈值，进入压缩。
6. 优先让模型生成结构化摘要。
7. 摘要失败时使用确定性折叠。
8. 保存压缩边界。
9. 重新注入最近读取的关键文件片段。

### 为什么使用真实令牌锚点

只按字符数估算会受到：

- 中英文差异；
- 模型分词差异；
- 工具结构差异；
- 缓存和协议额外内容影响。

项目使用最近一次真实令牌统计作为基础，只估算新增消息，从而比全量字符估算更稳定。

### 上下文超限后的恢复逻辑

当模型服务明确返回上下文过大：

1. 强制执行一次高强度压缩。
2. 重新请求模型。
3. 如果仍然过大，按完整交互轮次移除最旧内容。
4. 不拆开工具请求和对应结果。
5. 如果单条消息本身过大，保留头尾并收缩中间。
6. 每次收缩后重试。
7. 重试次数达到上限后明确失败。

### 为什么恢复必须有边界

如果没有上限，可能出现：

上下文过大  
→ 压缩  
→ 仍然过大  
→ 再压缩  
→ 无限循环

因此项目限制恢复次数，并在没有可进一步压缩内容时停止。

### 压缩后的信息保护

优先保留：

- 当前用户目标；
- 系统安全规则；
- 任务计划；
- 最近环境观察；
- 工具请求与结果关系；
- 最近读过的关键文件；
- 已经做出的重要决策；
- 未完成事项和阻塞原因。

## 11. 长期记忆

> Markdown 保存真相，Chunk 缩小检索粒度，Exact 保住确定性，BM25 保住关键词，Dense 补足语义召回，RRF 融合不同排名，Reranker 提高精度，Topic 聚合恢复上下文，Passage Budget 控制最终注入。

### 长期记忆目标

跨独立会话保留稳定且可复用的信息，例如：

- 用户偏好；
- 项目事实；
- 已确认决策；
- 长期约束；
- 经过多次任务验证的经验。

不应保存：

- 临时对话；
- 一次性命令输出；
- 未验证猜测；
- 敏感凭据；
- 当前任务很快失效的信息。

### 启用边界

- `MemoryConfig` 的内置默认值是关闭；当前项目的 `agent.toml` 将其开启。
- `AGENT_MEMORY` 和 `--memory` / `--no-memory` 可以覆盖启用状态；检索、抽取和巩固参数来自配置文件。
- 关闭时不创建存储、召回器和抽取器，主循环按无长期记忆的方式运行。
- 用户请求中明确出现“忽略记忆”或“不要使用记忆”时，本轮跳过自动召回。
- 记忆召回、抽取、巩固或索引故障都是可降级能力，不应使原本可执行的主任务失败。

### 存储模型与隔离

| 组成 | 当前实现 |
|---|---|
| 权威数据 | 每个主题一个带 YAML 元数据的 Markdown 文件，保存 `id`、名称、描述、类型、时间、置信度、标签、来源、显式写入和验证状态等信息 |
| `MEMORY.md` | 自动生成的人类可读主题摘要，最多 200 行且不超过 25 KB；它不是权威数据，也不限制主题枚举和检索 |
| 私有记忆 | 默认位于 `~/.polaris/projects/<project-id>/memory/private/`，按规范化项目标识隔离；仓库内配置不能把它重定向到任意外部路径 |
| 团队记忆 | 位于当前 checkout 的 `.polaris/memory/team/`，可以由 Git 审阅和同步，但系统不会自动提交或推送 |
| 派生索引 | 位于 `~/.polaris/indexes/<memory-root-hash>/<index-fingerprint>/`，包含 SQLite 检索库和可选 USearch ANN 旁路文件，可删除后从 Markdown 重建 |
| 兼容迁移 | 旧 `memory.jsonl` 可迁移为主题 Markdown；迁移失败不会阻塞 Agent，源文件仍保留 |

命名智能体还可以按 `user`、`project` 或 checkout-local 范围建立独立记忆目录。主智能体默认使用项目私有记忆；团队记忆默认通过显式工具写入，不做自动抽取。

### 长期记忆完整流程

```text
任务开始
→ 扫描主题 Markdown，并按内容哈希增量同步派生索引
→ 根据当前请求分别获得 Exact、BM25 和 Dense 候选
→ 使用加权 RRF 融合，再由 BGE Reranker 重排
→ 按 Topic 聚合为少量完整 Passage，并在字节预算内注入
→ Agent 将它作为不可信历史上下文完成任务
→ 自然结束后，仅对抽取游标之后的新对话做增量抽取
→ 去重和秘密扫描通过后，原子写入主题 Markdown
→ 同时满足时间与会话门槛时，执行遗忘、合并和洞察生成
```

### Markdown 分块与派生索引

主题内容先按标题、段落和围栏代码块切分，再打包成默认约 384 个近似 token 的 Chunk，相邻 Chunk 保留 64 token 重叠。这样既保留 Markdown 结构，也避免把整篇主题都塞给检索模型。

索引指纹覆盖数据库结构、分块器、词法规范化、Chunk 参数和 Embedding 模型。模型或分块逻辑升级后会进入新的索引目录，不会把不兼容向量混在一起。索引保存：

- 文档元数据和 Chunk；
- 路径、标识符、版本、提交号、错误码和引号短语等 Exact Atom；
- SQLite FTS5 数据；
- Dense Embedding、诊断信息和可恢复的后台向量任务；
- 大规模集合使用的不可变 USearch ANN 代际文件。

手工新增、修改、归档或删除 Markdown 后，下次同步会通过 SHA-256 发现变化。SQLite 和 ANN 都只是加速层，丢失或损坏时可以从 Markdown 重建。

### 混合召回与排序

默认本地 CPU 检索分为五级：

1. **Exact 与结构化过滤**
   - 精确匹配路径、代码标识符、版本、提交号、错误码和引号短语；
   - 支持按 `id`、`tag`、`type`、`source` 过滤；
   - 显式过滤命中和 Exact 命中具有硬优先级。

2. **BM25 词法召回**
   - 使用 SQLite FTS5；
   - 字段权重为名称 4、标签 3、描述 2、正文 1；
   - 文本先做 NFKC、大小写折叠和路径分隔符规范化；
   - 中文生成二元和三元字符片段，代码标识符同时保留整体形式和拆分形式。

3. **BGE-M3 Dense 语义召回**
   - 小于 10,000 个合格向量的集合采用受内存约束的分批精确余弦扫描；
   - 更大集合使用内存映射的 USearch HNSW 召回候选，再读取 SQLite 中的 FP32 向量做精确重算；
   - 过滤条件过于选择性或 ANN 不可用时回退精确 Dense 扫描。

4. **加权 RRF 融合**
   - Exact、BM25、Dense 的权重分别为 2、1、1；
   - 用排名而不是直接混合不同模型的原始分数，降低分数量纲不一致的问题；
   - 每个 Topic 最多保留三个候选 Chunk 进入后续阶段。

5. **BGE Reranker 与 Topic 聚合**
   - 默认重排前 24 个 Chunk，并过滤普通低相关结果；
   - 同一 Topic 最终最多形成两个合并且不重叠的 Passage；
   - 自动召回默认返回 5 个 Topic，只注入这些完整 Passage，不注入 `MEMORY.md` 或整篇主题。

最终普通结果主要按相关性排序；置信度、是否已验证、是否显式写入、更新时间和稳定 Chunk ID 只用于打破并列。存储的重要性和访问新近度不参与检索相关性，当前 Markdown 主路径的召回也不会为了“强化记忆”而改写持久化访问次数。因此不能再把召回描述为“相关性 + 重要性 + 时效性”的线性加权，也不能声称“越常召回越靠前”。

### 召回注入与可观测性

- 没有合格结果时不生成记忆块。
- 注入块位于主系统提示之后、项目上下文和当前任务之前，并标记为固定的系统记忆上下文。
- 注入内容明确声明为“不可信、可能过期”，不能授予权限、修改系统规则或覆盖当前请求。
- 默认内容预算为 64 KB；放不下的 Passage 整段跳过，不从中间截断 UTF-8 或正文。
- `memory_search` 可显式查询私有或团队记忆，并支持过滤、解释轨迹和按需返回完整主题；自动召回只使用 Passage。
- `memory_recall` 轨迹记录各阶段数量、耗时、索引覆盖率、模型与索引指纹、降级原因和最终 ID，不记录查询原文、Passage、完整文档或 Embedding。

### 记忆抽取

主循环自然结束后，由模型从尚未处理的新对话中提取可跨会话复用的信息。每个会话维护持久化抽取游标，成功解析并写入后才推进，避免连续聊天反复抽取旧消息。

抽取模型可以提出：

- `create`：创建新记忆；
- `update`：更新已给出 ID 的主题；
- `archive`：把已给出 ID 的主题移入归档；
- `forget`：把已给出 ID 的主题移入可恢复回收区；
- 内容、记忆种类、生命周期重要性和标签，运行编号作为来源写入。

以下内容不进入抽取：

- 系统提示；
- 工具输出；
- 压缩生成内容；
- 自动召回和项目上下文；
- 子智能体侧链及临时运行状态。

如果本轮已经通过 `memory_write` 或 `memory_forget` 显式修改记忆，自动抽取会推进游标但跳过写入，避免同一事实被保存两次。抽取响应格式错误、模型调用失败或没有值得保留的信息时返回空结果，不影响已经完成的任务。

### 去重

自动创建新记忆前会与已有主题做词法重合比较，达到默认 `0.85` 阈值时跳过。当前去重使用与中文兼容的 Unicode/CJK 词法 token，但还没有使用 Dense Embedding 做语义去重。

显式写入不走这层自动去重，因为它代表用户或 Agent 的明确持久化意图；可以通过目标 ID 更新已有主题。

### 显式维护接口

- Agent 工具：`memory_search`、`memory_write`、`memory_forget`。
- 聊天命令：`/memory list|show|search|add|edit|forget|validate`。
- CLI：`polaris memory list|show|search|add|edit|forget|validate|migrate`。
- 索引和模型检查：`polaris memory index status|rebuild`、`polaris memory models status|install`。
- 手工编辑主题 Markdown 后可以校验并重建索引，不需要把 SQLite 当成可编辑数据源。

### 记忆巩固

巩固可以手工执行 `polaris dream`，也可以自动触发。自动模式默认要求距上次成功巩固至少 24 小时，并且累计至少 5 个新会话；两个条件必须同时满足，并使用跨进程锁避免重复运行。

1. **遗忘**
   - 按默认 14 天半衰期降低生命周期重要性；
   - 只有衰减后低于阈值且访问保护计数不足的弱记忆才从活动集合移入 `archive/`；
   - 显式、已验证和团队主题会获得保护，不会被普通弱记忆规则直接淘汰。

2. **合并**
   - 按词法相似度聚合同类主题；
   - 保留重要性最高的主题作为主记录，合并标签和生命周期元数据；
   - 合并减少重复，但不等于已经解决语义冲突。

3. **洞察**
   - 可选地让模型从至少两条存量记忆中生成最多两条新的高层 `insight`；
   - 新洞察仍需经过去重，失败时跳过，不影响前两阶段。

生命周期重要性只服务于巩固，不参与在线检索排序。当前主路径又不会因一次召回更新持久化访问计数，因此面试时应把“在线相关性”和“离线生命周期”明确分开。

### 模型安装与分级降级

- Embedding 和 Reranker 使用固定版本、带 SHA-256 校验的 INT8 CPU ONNX 模型包，不允许运行远程模型代码。
- 标准安装器安装约 1.15 GB 的模型与 Tokenizer；离线环境可以提供模型包。
- 向量尚未补齐时，Exact 和 BM25 立即可用，后台任务可继续填充 Embedding。
- Reranker 缺失时使用 RRF 排序。
- ANN 缺失、陈旧或损坏时回退分批精确 Dense 扫描，并安排重建。
- SQLite/FTS 索引损坏时回退完整 Unicode 词法扫描，并安排重建。
- 只有显式使用安装器的 `--skip-memory-models` 才表示接受纯词法运行；运行时仍会把实际降级原因写入轨迹。

### 安全与数据治理

- 记忆路径拒绝空字节、`..`、UNC/网络根、盘符根目录和符号链接逃逸。
- 写入使用文件锁、`fsync` 和原子替换，防止多进程互相覆盖或留下半个文件。
- 写入前扫描常见秘密和凭据；诊断信息不回显秘密值。
- 格式错误、冲突标记、重复 ID 和超大主题会被跳过并产生可见诊断。
- `forget` 移入 `.trash/`，巩固淘汰移入 `archive/`，二者都不是立即不可恢复的物理删除。
- 卸载默认只删除安装器拥有的模型和派生索引，不删除权威 Markdown，除非用户明确要求清除全部数据。

### 当前长期记忆的主要不足

#### 召回能力已具备，正式评估仍不足

中文二/三元字符、Exact、BM25、BGE-M3 Dense 和 BGE Reranker 已经落地，不能再描述成“只支持英文词法”或“没有向量检索”。当前真正缺少的是版本化的中文、英文、代码和混合语料评估集，以及 Recall@K、MRR/NDCG、Reranker 精度、ANN Recall、延迟和降级率的持续报告。

#### 自动抽取和巩固仍有不确定性

抽取、更新和洞察由大模型生成，仍可能遗漏事实、写入过度概括的内容或误判新旧关系。自动去重与合并目前主要依赖词法重合，即使中文已经可切分，也不能可靠识别跨语言同义、语义冲突、事实演变和时间有效期。

#### 本地模型与索引有资源成本

本地模型包约 1.15 GB，首次建索引、后台 Embedding、大规模 ANN 构建和 CPU Reranker 都有磁盘、内存与延迟成本。需要继续量化冷启动、增量更新和不同数据规模下的性能。

#### 隔离边界不是完整的企业多租户系统

当前已有私有、项目、团队和命名智能体目录隔离，也有安全路径和可恢复删除，但仍是本地文件系统边界。商业化还需要服务端身份认证、细粒度 ACL、租户级加密与审计、集中保留策略、远程同步和分布式索引一致性。

## 12. 多智能体协同

### 两种多智能体模式

#### 一次性子智能体

适合：

- 独立调查；
- 大范围搜索；
- 多个互不依赖的分析；
- 需要保持主上下文简洁的子任务。

流程：

主智能体定义完整子任务  
→ 为子智能体选择只读或可写能力  
→ 可选择更便宜的模型  
→ 可选择共享工作区或独立工作区  
→ 子智能体在干净上下文中运行  
→ 只把最终结论返回主智能体

限制：

- 子智能体不能继续创建普通子智能体；
- 存在最大深度；
- 默认不重复启用长期记忆；
- 默认不重复加载技能；
- 工具范围比父智能体更窄。

#### 显式团队协作

适合：

- 需要角色分工；
- 需要持续同步；
- 需要任务状态；
- 需要多个结果汇总；
- 任务持续时间较长。

流程：

建立团队  
→ 创建任务  
→ 分配负责人  
→ 启动成员  
→ 成员读取自己的消息  
→ 成员更新任务状态  
→ 成员向负责人发送结果  
→ 负责人查看团队全局状态  
→ 汇总最终输出

### 团队共享状态

- 团队目标；
- 团队成员；
- 任务列表；
- 负责人；
- 任务优先级；
- 任务进度；
- 任务结果；
- 团队事件；
- 每个成员的消息箱；
- 未读位置。

### 并发安全

多个智能体同时更新共享状态时使用文件锁，避免：

- 消息互相覆盖；
- 任务状态丢失；
- 负责人分配冲突；
- 事件记录损坏。

### 多智能体资源治理

- 所有智能体共享模型并发上限；
- 所有智能体共享请求速率限制；
- 子智能体继承父任务剩余时间；
- 每个智能体有独立运行日志；
- 父子日志通过运行编号关联；
- 子智能体权限不能超过父智能体；
- 可写子任务可以使用独立版本控制工作区。

### 为什么使用独立工作区

多个智能体同时修改同一代码目录可能产生：

- 文件覆盖；
- 未提交修改冲突；
- 测试相互干扰；
- 难以确认每个智能体做了什么。

独立工作区让每个智能体拥有独立分支和目录，结束时再汇总：

- 是否产生修改；
- 是否产生新提交；
- 修改摘要；
- 是否需要保留工作区；
- 是否存在冲突。

### 什么时候不应使用多智能体

- 任务很小；
- 子任务强依赖；
- 需要共享大量上下文；
- 多个成员会修改相同文件；
- 子任务无法定义明确交付物；
- 协调成本高于并行收益。

### 面试总结

> 多智能体不是默认更强，而是一种高成本执行策略。是否使用应由质量提升、额外令牌、延迟、冲突率和协调开销共同决定。

## 13. 权限、沙箱与安全

### 为什么 Agent 安全不能只依赖模型

模型可能：

- 误解用户意图；
- 受工具输出中的恶意指令影响；
- 调用过于宽泛的命令；
- 访问敏感文件；
- 把数据发送到外部网络；
- 让子智能体获得过高权限。

因此安全边界必须由确定性系统执行。

### 权限判断顺序

1. 检查工具参数结构。
2. 刷新管理员策略。
3. 检查当前权限模式是否被管理员禁止。
4. 检查管理员明确拒绝规则。
5. 检查普通明确拒绝规则。
6. 检查无人值守模式是否拥有有效沙箱。
7. 检查子智能体是否超过父智能体权限。
8. 检查计划模式的只读要求。
9. 检查路径是否越界或涉及敏感内容。
10. 检查网络目标和域名策略。
11. 检查明确要求询问的规则。
12. 执行工具自身的参数级安全判断。
13. 检查当前会话临时授权。
14. 检查明确允许规则。
15. 根据工具风险和当前模式决定允许、拒绝或询问。
16. 只有剩余的可分类动作才能交给自动安全判断。

### 权限模式

| 模式 | 运行逻辑 |
|---|---|
| `default`（默认模式） | 读取通常自动允许，写入和危险操作通常询问 |
| `acceptedits`（接受编辑模式） | 额外自动允许系统原生文件编辑工具 |
| `plan`（计划模式） | 严格只读，只允许调查和专用计划能力；计划经人工批准后才恢复执行权限 |
| `auto`（自动模式） | 可分类的剩余操作由安全分类器判断 |
| `dontask`（不询问模式） | 任何需要询问的操作直接拒绝 |
| `bypass`（绕过模式） | 允许普通剩余操作，但管理员拒绝、敏感路径和其他硬性规则仍生效 |

### 自动安全判断的边界

自动判断不能推翻：

- 管理员拒绝；
- 明确拒绝规则；
- 明确询问规则；
- 敏感路径保护；
- 受保护项目文件；
- 必须由用户交互确认的动作；
- 子智能体权限上限。

如果自动判断不可用：

- 顶层交互会话可以回退人工确认；
- 无界面运行默认拒绝；
- 子智能体默认拒绝。

### 沙箱与权限的区别

| 权限 | 沙箱 |
|---|---|
| 判断是否允许执行 | 限制执行后能影响的范围 |
| 属于策略层 | 属于操作系统隔离层 |
| 可以要求人工审批 | 无法替代业务审批 |
| 检查动作语义 | 控制文件、网络和进程能力 |

正确关系：

权限允许  
不代表无限执行  
仍需沙箱限制实际影响范围

沙箱属于确定性 Workflow，因为它不是依靠模型承诺“只做安全操作”，而是由容器或操作系统后端实际限制：

- 能读取哪些目录；
- 能写入哪些目录；
- 能否访问网络；
- 能否启动其他进程；
- 是否可以影响宿主机环境。

权限负责回答“这个动作能不能执行”，沙箱负责回答“即使执行，最大能影响多大范围”。二者不能相互替代。

### 沙箱层级

沙箱后端统一实现 `available()`、`isolates()`、`prepare()`、`wrap()`、`reset()` 和 `teardown()` 生命周期，但隔离强度与平台支持不同。

| 层级 | 实现 | 主要平台 | 隔离特点 | 当前边界 |
|---|---|---|---|---|
| Native | Linux `bubblewrap`；macOS `sandbox-exec` | Linux、macOS | 同内核、启动快，可限制文件和网络 | Windows Native Strategy 是 `NoopBackend`，不提供真实隔离 |
| Container | Podman、Docker、nerdctl | 跨平台；Windows 使用 WSL2 Linux Container 或显式 Hyper-V Container | 每次命令使用临时 OCI 容器，隔离文件系统、网络和进程能力 | 依赖可用 Runtime、后台 VM / Daemon 和镜像 |
| VM | Linux Kata、Windows Hyper-V、macOS Lima | 显式配置的平台 | 独立 Guest；Windows 可在任务前恢复 Checkpoint | 重、强依赖宿主环境，`auto` 不会自动选择 |
| No-op | 原样返回命令 | 所有平台 | 没有 OS 隔离，仅保留权限和路径策略 | 用于关闭、缺依赖或允许降级的情况 |

后端选择不是简单判断操作系统，而是同时检查“依赖可用”和“确实隔离”：

| `backend` 配置 | 候选顺序 |
|---|---|
| `auto` | Container → Native → No-op；永远不自动进入 VM |
| `native` | Native → No-op |
| `container` | Container → Native → No-op |
| `vm` | VM → Container → Native → No-op |

Windows 的 Native Backend 虽然可以构造，但其 Strategy 是 No-op，`isolates()` 返回 `false`，所以 `auto` 不会把它误判成真实沙箱。在 Windows 上，`auto` 要获得真实隔离，必须找到可工作的 Podman、Docker 或 nerdctl。

<a id="sandbox-lifecycle"></a>

### 沙箱的完整运行机制

完整链路如下：

```text
读取默认、用户、项目和 agent.local.toml 配置
→ 应用环境变量与 CLI 覆盖
→ 按 backend 构造候选链
→ 同时检查 available() 与 isolates()
→ 创建按“配置指纹 + 工作区”共享的 SandboxManager
→ prepare() 验证 Runtime、镜像或 VM
→ 把 Manager 绑定到 SandboxAware 工具
→ 权限管线判断本次调用能否执行
→ wrap() 按 ExecutionScope 生成隔离启动参数
→ ProcessSupervisor / 子进程执行包装后的 argv
→ 记录实际 Backend、是否隔离及执行结果
→ 会话结束时 teardown()
```

#### 第一阶段：配置解析

配置优先级是：

```text
内置默认
→ 用户配置
→ 项目 agent.toml
→ Git 忽略的 agent.local.toml
→ AGENT_SANDBOX 等环境变量
→ --sandbox / --no-sandbox / --sandbox-backend
```

项目仓库中的配置不能未经信任就放宽 `excluded_commands`、自动允许和无沙箱运行等安全项；本地 `agent.local.toml` 用于保存用户明确选择的覆盖。

#### 第二阶段：候选选择与启动准备

`SandboxManager` 构造时先按候选链检查：

- Runtime 或平台命令是否存在；
- 后端是否声明自己真正提供隔离；
- Native Strategy 是否只是 No-op；
- 显式 VM Provider 的基础依赖是否存在。

这个阶段只足以选出“名义后端”。随后 `prepare()` 才验证真实运行条件：

- Container：执行镜像检查；镜像缺失且 `auto_pull=true` 时尝试拉取；
- Hyper-V：检查 `guest_host`，调用 PowerShell 检查或创建基础 Checkpoint；
- Lima：启动指定 VM；
- Kata：检查 OCI Runtime 并准备 Container Image。

Manager 按“完整配置 + 工作区”在进程内共享；`prepare()` 幂等，因此主 Agent、子 Agent 和同配置实例不会重复拉取镜像或启动重型后端。

#### 第三阶段：权限预检与单次调用 Scope

工具执行前，权限系统会取得真实 `SandboxState`：

- `enabled`：当前是否真的存在隔离后端，而不只是配置写了 `enabled=true`；
- `backend`：实际选择的 `container`、`native`、`vm` 或 `noop`；
- `will_sandbox`：这一条命令是否会进入沙箱；
- `excluded`：是否命中 `excluded_commands` 而在宿主机执行；
- `auto_allow_enabled`：是否允许“只因将被沙箱隔离”而跳过询问。

当前默认 `auto_allow_command_if_sandboxed=false`，所以即使命令会进入容器，沙箱也不会自动替代权限审批。

每次命令使用不可变的 `ExecutionScope` 描述：

- 当前 Workspace；
- 额外只读或可写根目录；
- Git Common Directory；
- 私有临时目录；
- 是否允许网络；
- Workspace 是否可写。

Manager 为这一调用复制配置并合并 Scope，不直接修改全局配置，避免并发工具相互污染安全边界。

#### 第四阶段：命令包装与监督执行

`bash` 和 `powershell` 先把用户命令解析为显式 argv，再调用：

```python
sandbox.wrap(
    argv,
    False,
    command=原始命令,
    scope=ExecutionScope.for_workspace(workspace, network="deny"),
)
```

如果当前命令应该隔离，Backend 把 argv 包装成 Container / Native Launcher / SSH Launcher；随后仍由统一 `ProcessSupervisor` 负责：

- 前台或后台运行；
- 单一超时；
- 输出日志和预览限制；
- 取消与进程树清理；
- `task_output` 查询；
- `task_stop` 终止。

`run_tests` 使用显式 pytest argv，并以 `command=None` 调用 `wrap()`，因此只要真实沙箱启用就会隔离，不参与 `excluded_commands` 的命令字符串匹配。LSP 使用更严格 Scope：Workspace 只读、网络拒绝，只给语言服务一个私有可写临时目录。

模型若传入 `dangerously_disable_sandbox=true`，也不能自行绕过隔离：

- `allow_unsandboxed_commands=false` 时确定性拒绝；
- 允许该 Escape Hatch 时仍必须人工确认；
- `excluded_commands` 也只跳过沙箱，不跳过普通权限规则。

#### 第五阶段：重置、降级与清理

- Container 使用 `run --rm`，每次命令结束后删除临时容器；
- VM 在 `reset_each_task=true` 时于任务边界恢复基础 Snapshot；
- Manager 会对当前及已经被热重配置替换的旧后端调用 `teardown()`；当前 Container 主要依靠 `--rm` 清理，Hyper-V / Lima Strategy 尚未实现完整的主动关机清理；
- 后台任务仍由 Supervisor 在会话关闭时统一终止。

<a id="windows-sandbox"></a>

### Windows 中的具体实现

当前 Windows 主路径不是 AppContainer、Windows Sandbox 或 Job Object，而是：

```text
Windows Polaris 进程
→ Podman / Docker / nerdctl CLI
→ WSL2 Linux Container Runtime
→ 临时 Debian Container
→ 在映射后的 Workspace 中执行命令
```

路径映射示例：

```text
宿主机：E:\ZNGZ\Code_copy\learning_proj\AgentwithLLM
Guest： /mnt/e/ZNGZ/Code_copy/learning_proj/AgentwithLLM
```

Container Backend 生成的命令结构近似为：

```text
podman run --rm --init
  -v <Windows工作区>:<WSL2工作区>
  -w <WSL2工作区>
  --network none
  --read-only
  --tmpfs /tmp
  --cap-drop ALL
  --security-opt no-new-privileges
  docker.io/library/debian:stable-slim
  <原始命令argv>
```

硬化语义：

| 控制项 | 当前默认 |
|---|---|
| 容器生命周期 | `--rm`，单次命令临时容器 |
| 工作目录 | 只显式挂载 Workspace；当前 Workspace 默认可写 |
| Root Filesystem | `--read-only` |
| 临时目录 | `/tmp` 使用 tmpfs |
| Linux Capability | `--cap-drop ALL` |
| 提权 | `no-new-privileges` |
| 网络 | `allowed_domains=[]` 且不允许本地监听时使用 `--network none` |
| 资源限制 | 支持 Memory、CPU、PID 配置；当前留空，尚未限制 |

需要准确说明网络边界：当前 Container Backend 在没有网络需求时能做到 `--network none`；但只要配置任一 `allowed_domains` 或允许本地监听，就切换到普通 `bridge` 网络。项目还没有把域名列表下沉成容器内代理或逐域防火墙，因此“允许一个域名”在 Container OS 层并不等于“只允许这一个域名”。原生 Web 工具仍有独立的域名和 SSRF 检查。

Windows 还有一条显式 VM 路径：

```text
backend = "vm"
→ Hyper-V Linux Guest
→ prepare() 创建 / 确认基础 Checkpoint
→ reset() 在任务前 Restore-VMSnapshot
→ wrap() 通过 SSH 在 Guest Workspace 执行
```

这条路径不会被 `auto` 选择，并要求提前配置可用的 `guest_host`、VM、共享 Workspace 和 SSH。

### 当前项目配置与本机实测状态

当前有效配置要点：

| 配置 | 当前值 | 含义 |
|---|---|---|
| `permission` | `default` | 读取通常允许，写入和危险操作仍询问 |
| `sandbox.enabled` | `true` | 请求启用沙箱 |
| `sandbox.backend` | `auto` | Container → Native → No-op |
| `fail_if_unavailable` | `false` | 后端准备失败时允许降级 |
| `auto_allow_command_if_sandboxed` | `false` | 沙箱不替代审批 |
| `allow_unsandboxed_commands` | `true` | 显式 Escape Hatch 可请求，但必须确认 |
| `excluded_commands` | `[]` | 没有预设宿主机直跑命令 |
| Container Runtime | `auto` | Podman → Docker → nerdctl |
| Container Image | `debian:stable-slim` | 缺失时允许自动拉取 |
| `windows_isolation` | `wsl2` | 使用 Linux Container 路径映射 |
| VM `guest_host` | 空 | Hyper-V VM 路径当前不可用 |

截至 **2026-07-31** 对本机实际检查：

- 已安装 Podman 5.8.3；
- 存在 `podman-machine-default`，类型为 WSL；
- Machine 的 `LAST UP` 为 `Never`；
- `podman info` 无法连接 Runtime；
- Sandbox Image 检查也无法完成。

因此当前启动时会出现两阶段状态：

```text
构造阶段：发现 podman.exe
→ 名义选择 ContainerBackend
→ prepare() 执行 image inspect / pull
→ Podman Machine 未运行，准备失败
→ fail_if_unavailable=false
→ 实际替换为 NoopBackend
→ default 权限模式下继续运行，但命令没有 OS 沙箱隔离
```

这说明“配置开启”“代码支持”和“本轮真实生效”是三个不同结论。当前准确表述应是：

> 项目已经实现并开启 Windows OCI Container Sandbox，但本机 Podman Machine 当前未就绪，所以实际运行会降级为 No-op；权限规则仍生效，但不能把这次运行称为已沙箱隔离。

若要把沙箱作为强安全门，应：

1. 启动并验证 Podman Machine；
2. 确认 `debian:stable-slim` 可检查或拉取；
3. 用 Health Check 验证 Container Runtime 与 Image，并检查运行日志中的实际 Backend；
4. 将 `fail_if_unavailable=true`，避免容器失效后继续在宿主机执行。

`auto`、`dontask`、`bypass` 属于无人值守权限模式。即使 `fail_if_unavailable=false`，这些模式在没有真实沙箱时仍默认拒绝构造或要求交互式明确确认；只有显式、可审计的 `allow_unattended_unsandboxed` Opt-out 才能放行。

<a id="sandbox-boundaries"></a>

### 沙箱覆盖范围与真实边界

不是每个工具都通过 OCI Container 执行。

| 工具 / 能力 | 是否经过 SandboxManager | 主要安全边界 |
|---|---|---|
| `bash`、`powershell` | 是 | 权限规则 + 命令语法分析 + Container / Native / VM |
| `run_tests` | 是 | 参数限制 + 权限 + Sandbox argv |
| `lsp` 语言服务子进程 | 是 | Workspace 只读 Scope + 私有 Temp + 禁网 |
| `read_text_file`、`glob`、`search_text` | 否 | `WorkspacePathMixin`、敏感路径和权限规则 |
| `write_text_file`、`edit_file`、`multi_edit`、`apply_patch` | 否 | 工作区路径、符号链接、安全规则、审批和 Diff 审计 |
| MCP Tool | 否 | MCP Server 级风险、权限和外部 Server 自身隔离 |
| `web_fetch`、`web_search` | 否 | 域名规则、SSRF 防护、重定向逐跳检查和审批 |
| Memory、Team、Scheduler | 否 | 专用路径 / 数据模型、权限与并发锁 |

必须主动说明的当前局限：

1. **Windows Native 不隔离**
   - 没有实现 AppContainer 或同级 Windows 原生沙箱；没有可用 Container 时会进入 No-op。
2. **Windows Container 尚缺本机端到端验证**
   - 当前测试重点覆盖 Backend 选择、路径映射和生成的 `run` argv；
   - 当前本机 Podman 从未成功启动，不能用 Mock 单测证明真实 Windows 命令已经在 Debian Container 中正确执行；
   - Bash / PowerShell 在宿主机解析出的可执行路径怎样映射为 Guest 内命令，仍需要真实 Podman E2E 测试确认。
3. **VM 生命周期实现仍不完整**
   - Hyper-V 会调用 Checkpoint / Restore，Lima 会调用启动命令，但当前 Strategy 没有实现完整的主动 Teardown；
   - PowerShell / VM 生命周期命令的布尔失败结果尚未全部升级为 Fail-closed 错误，因此 VM 层目前更接近实验性后端。
4. **Container 域名允许是粗粒度**
   - 非空域名列表当前只会打开 Bridge，不是逐域网络 Enforcement。
5. **细粒度文件策略的后端语义不完全一致**
   - Bubblewrap / Seatbelt 会处理 `deny_read`、`deny_write` 等路径；
   - Container 当前主要依靠“只挂载 Workspace 和显式额外目录”，尚未把每个子路径拒绝规则都转换成独立 Mask / Mount。
6. **MCP 与原生文件工具不在命令容器内**
   - 必须继续依赖权限、路径限制、Server 自身策略和审计，不能把 Sandbox 的安全结论外推给全部工具。
7. **Workspace 默认可写**
   - 沙箱保护宿主机其他区域，但获准的恶意命令仍可能破坏工作区；Git、Worktree、备份和人工 Review 仍有必要。
8. **当前默认允许降级**
   - `fail_if_unavailable=false` 更偏开发可用性，不适合把隔离当成硬合规要求的生产环境。

面试中最稳妥的总结：

> Polaris 把沙箱实现为权限之后的 OS Enforcement Layer。运行时根据配置选择 Native、Container 或 VM，启动时真实验证依赖和镜像，再按每次调用的 ExecutionScope 包装命令。Windows 的主路径是 WSL2 上的 Podman / Docker Linux Container，默认只挂载工作区、根文件系统只读、禁网、去除 Capability，并保留独立权限审批。当前本机因为 Podman Machine 未启动而降级为 No-op，所以我会明确区分架构能力和实际生效状态；生产环境应启用 fail-closed，并补齐 Windows 端到端与逐域网络隔离。

### 其他安全措施

- 工作区路径限制；
- 敏感文件保护；
- 网络域名允许和阻止策略；
- 网页请求的内部地址防护；
- 重定向后重新检查目标；
- 运行日志敏感信息脱敏；
- 项目配置的信任确认；
- 项目说明不能覆盖系统安全规则；
- 工具输出按不可信信息处理。

### 权限审计由运行时确定性记录

审计不能依赖模型事后描述“我刚才做了什么”，而应由运行时在每个关键动作发生时按固定结构记录。一次权限审计至少包含：

- 调用了哪个工具；
- 当前使用哪种权限模式；
- 最终决策是 `ALLOW`、`ASK` 还是 `DENY`；
- 命中了哪条规则；
- 决策来源是管理员策略、用户规则、工具判断、自动分类器还是人工确认；
- 是否在沙箱内执行，以及使用了哪类隔离后端；
- 是否经过人工确认；
- 工具最终成功还是失败。

对于命令、文件内容、Token、URL 参数和其他敏感数据，日志只保存必要的摘要、哈希或脱敏值，不把秘密原文完整写入审计轨迹。这样既能解释“为什么允许或拒绝”，也不会让日志本身成为新的泄密面。

### 编辑工具调用的完整安全链路示例

以模型生成一次文件编辑工具调用为例：

```text
模型生成编辑行动
→ Schema 检查工具名和参数
→ 解析目标路径并检查是否仍位于工作区
→ 检查符号链接逃逸及 .env、私钥等受保护文件
→ 检查 plan 只读约束和父子 Agent 权限上限
→ 根据显式规则与当前模式决定允许、询问或拒绝
→ 在限定文件系统范围内执行
→ 记录权限决策、修改摘要和执行结果
→ 将成功或失败作为 Observation 返回模型
```

这个例子体现了确定性系统的职责：模型只负责提出动作，是否执行、在哪里执行、记录什么以及失败后怎样反馈，都由运行时规则控制。

## 14. 并发、限流与稳定性

### 工具并发

多个工具行动可能在同一模型轮次出现。

系统不是全部并发，而是先分析资源冲突。

#### 可以并发的例子

- 读取两个不同文件；
- 搜索两个不同目录；
- 启动两个只读子智能体；
- 查询互不相关的外部资源。

#### 不应并发的例子

- 同时写入同一文件；
- 一个读取、一个写入同一文件；
- 同时更新同一个团队任务；
- 同时切换会话工作区；
- 未声明资源边界的高风险工具。

### 并发分组逻辑

1. 每个工具声明会读取或写入的资源。
2. 比较同一批工具的资源。
3. 只读与只读通常不冲突。
4. 只要存在写入重叠，就视为冲突。
5. 无冲突工具放入同一并发批次。
6. 有冲突工具进入后续批次。
7. 独占工具单独执行。

### 模型并发

主智能体、子智能体、摘要任务和辅助模型可能同时请求模型服务。

系统使用：

- 共享并发信号量；
- 共享请求速率限制；
- 所有子智能体共用同一资源预算。

避免：

- 多智能体瞬间打满服务；
- 超过供应商并发限制；
- 请求风暴；
- 子智能体绕过主智能体预算。

### 模型请求重试

对以下故障进行有界重试：

- 请求过多；
- 部分服务器错误；
- 网络连接失败；
- 超时；
- 临时传输异常。

策略：

- 指数增加等待时间；
- 加入随机抖动，避免多个请求同时重试；
- 尊重服务端给出的等待时间；
- 设置最大等待时间和最大次数；
- 流式输出开始后不随意重试，避免重复半段内容。

### 时间控制

所有任务可以有总运行时间。

- 子智能体继承父任务剩余时间；
- 不会为每个子智能体重新分配完整时间；
- 接近上限时先提醒模型收尾；
- 到达上限后停止。

### 故障隔离

- 单个工具失败不会崩溃整个运行；
- 单个子智能体失败不会取消其他子智能体；
- 记忆和观察型扩展失败不影响主结果；
- 安全策略加载失败时拒绝高风险操作；
- 上下文恢复有最大次数；
- 停止扩展要求继续的次数有限。

## 15. 会话恢复、扩展能力与工程化

### 会话记录

每条消息保存：

- 唯一标识；
- 父消息标识；
- 消息角色；
- 内容；
- 工具关联信息；
- 压缩和运行元数据。

因此可以：

- 恢复历史会话；
- 继续最新会话；
- 从某个历史节点分叉；
- 保存压缩边界；
- 保存子智能体侧链。

### 会话记录与长期记忆的区别

| 会话记录 | 长期记忆 |
|---|---|
| 保存完整对话链 | 保存筛选后的稳定信息 |
| 用于恢复原任务 | 用于帮助未来独立任务 |
| 内容详细 | 内容精炼 |
| 按消息及父子关系组织 | 按主题 Markdown 组织，检索时再切成 Chunk |
| 按会话链恢复 | 通过 Exact、BM25、Dense、RRF 和 Reranker 做跨会话相关性召回 |

### 确定性的运行生命周期

除权限和沙箱外，整个 Agent 生命周期也由运行时按固定顺序治理：

```text
创建会话
→ 加载配置和权限策略
→ 初始化模型、工具、记忆和沙箱
→ 执行 ReAct 循环
→ 处理用户取消、运行超时或未捕获异常
→ 保存 Transcript、运行日志和最终指标
→ 停止后台任务
→ 关闭 MCP、LSP、Notebook、子 Agent 和子进程
→ 释放沙箱及其他资源
```

生命周期确定性主要解决四个问题：

1. **初始化完整**
   - 模型看到工具前，工具注册、权限策略和隔离后端已经就绪。
2. **异常可收尾**
   - 取消、超时或单个工具失败不会跳过持久化和清理阶段。
3. **状态可恢复**
   - Transcript、父子消息关系、运行编号和压缩边界由系统写入，而不是让模型自行总结。
4. **资源不泄漏**
   - 后台任务、外部协议连接、语言服务和子进程都在统一的退出阶段关闭。

因此，“确定性 Workflow”并不是拿固定步骤替代 ReAct 的动态决策，而是包围 ReAct，保证每次运行都经过一致的初始化、安全检查、持久化和资源释放。

### 生命周期扩展

系统在关键阶段提供扩展点：

- 用户输入提交；

- 工具执行后；

- 任务停止；

- 业务埋点；

### 外部工具协议

系统支持通过标准外部工具协议连接第三方能力。

价值：

- 统一第三方工具发现和调用；

它和工具的区别：

- 输入令牌成本；

- 缓存写入成本；
- 缓存读取成本；
- 子智能体成本；
- 摘要成本；
- 安全分类成本；

> 当前项目聚焦智能体运行层，因此没有为了技术栈而强行加入 PyTorch。训练侧如果需要做意图分类器、重排序模型、奖励模型、参数高效微调或策略优化，我会使用 PyTorch，并让训练系统与智能体运行系统通过数据集、模型服务和版本契约解耦。

- 张量和自动求导；
- 模型模块；
- 优化器；
- 数据加载；
- 混合精度；
- 梯度累积；
- 分布式训练；
- 参数高效微调；
- 训练与推理的差异。

### LangChain

当前项目没有直接使用 LangChain。

### 强化学习和自进化

当前项目没有强化学习训练闭环。

必须区分：

- 记忆巩固不是强化学习；
- 提示优化不是强化学习；
- 对照实验不是强化学习；
- 模型评分可以形成奖励信号，但不自动等于强化学习。

建议演进顺序：

1. 完整记录智能体轨迹和任务结果。
2. 建立可靠的自动验收。
3. 收集人工接受、拒绝和修改。
4. 形成偏好数据和奖励数据。
5. 先进行候选排序和最佳结果选择。
6. 再进行监督微调或偏好优化。
7. 在可控环境和可靠奖励下尝试策略优化。

### 奖励设计

奖励可以综合：

- 任务是否成功；
- 工具参数是否有效；
- 是否执行危险操作；
- 令牌成本；
- 运行延迟；
- 是否存在多余步骤；
- 是否需要人工接管。

### 奖励投机风险

例如只用“测试是否通过”作为奖励，智能体可能：

- 删除失败测试；
- 放宽断言；
- 跳过测试；
- 修改评估环境。

因此奖励必须同时检查：

- 真实任务结果；
- 文件修改范围；
- 安全约束；
- 测试完整性；
- 人工反馈。

## 19. 高频面试问题

### 问题一：项目为什么是 ReAct，而不是固定工作流？

回答要点：

- 代码任务的下一步依赖真实搜索、文件和测试结果；
- 无法在运行前确定所有步骤；
- ReAct 能根据环境观察动态调整；
- 对固定业务环节仍可使用确定性工作流；
- 最佳实践通常是工作流定义边界，Agent 在边界内自治。

### 问题二：如何防止 ReAct 无限循环？

回答要点：

- 模型不再请求工具时自然结束；
- 设置总运行时间；
- 可选最大轮数；
- 接近超时时提醒收尾；
- 限制停止阶段要求继续的次数；
- 工具失败返回明确原因；
- 后续可增加重复行动检测和进度评分。

### 问题三：如何判断工具是否可以并发？

回答要点：

- 每个调用声明读取和写入的资源；
- 只读与只读可以并发；
- 只要存在重叠写入，就分批执行；
- 未声明资源的工具保守独占；
- 多智能体修改代码时可使用独立工作区。

### 问题四：为什么权限不能只分读取和写入？

回答要点：

- 同一个命令工具既可以执行测试，也可以删除文件；
- 风险取决于具体参数；
- 需要参数级规则、路径检查和命令分析；
- 自动分类器不能推翻硬拒绝；
- 权限和沙箱必须同时存在。

### 问题五：短期记忆和长期记忆有什么区别？

回答要点：

- 短期记忆服务当前任务；
- 长期记忆服务未来独立任务；
- 会话记录用于恢复，不等于语义记忆；
- 任务清单是执行状态，不等于用户画像；
- 长期记忆以主题 Markdown 持久化，派生索引负责 Exact、BM25、Dense、融合和重排；
- 在线召回相关性与离线生命周期重要性是两套机制；
- 长期记忆还需要增量抽取、去重、可恢复遗忘、来源追踪和作用域隔离。

### 问题六：上下文过长怎么办？

回答要点：

- 平时根据真实令牌统计主动压缩；
- 优先生成结构化摘要；
- 摘要失败回退确定性折叠；
- 压缩后重新注入关键文件；
- 服务端拒绝时按完整轮次移除旧内容；
- 单条过大时保留头尾；
- 恢复次数有上限。

### 问题七：如何避免多智能体成本爆炸？

回答要点：

- 只拆分独立任务；
- 限制创建深度；
- 子智能体不能递归委派；
- 共享模型并发和速率预算；
- 共享总时间；
- 为简单子任务选择小模型；
- 评估多智能体相对单智能体的质量增益和额外成本。

### 问题八：如何评估 Agent，而不仅是模型？

回答要点：

- 最终任务成功是第一指标；
- 同时评估行动轨迹、工具、计划、记忆和安全；
- 统计延迟、令牌、重试和人工介入；
- 使用单个成功任务成本；
- 失败轨迹进入回归集；
- 用固定版本任务集做可重复对比。

### 问题九：工具输出里有恶意指令怎么办？

回答要点：

- 工具输出属于不可信环境信息；
- 不提升为系统规则；
- 权限和沙箱不依赖模型自觉；
- 敏感路径和网络策略由确定性系统执行；
- 使用攻击集评估越权和泄露。

### 问题十：如何实现 Agent 自进化？

回答要点：

- 先记录完整轨迹；
- 建立可靠验收；
- 聚类失败原因；
- 自动生成回归样本；
- 优化工具、提示、路由和记忆；
- 收集人工偏好；
- 再进行监督或偏好训练；
- 最后才考虑在线强化学习。

### 问题十一：为什么不直接使用 LangChain 或 AutoGen？

回答要点：

- 自主实现帮助掌握底层运行逻辑；
- 当前项目需要精细控制安全、并发和模型状态；
- 并不排斥框架；
- 固定流程和生态优先时可使用 LangGraph；
- 快速角色协作时可评估 AutoGen；
- 选型依据是业务复杂度、控制力、维护成本和生态。

### 问题十二：当前项目最大问题是什么？

回答要点：

- 缺少正式业务评估平台；
- 长期记忆已有中文与混合检索，但缺少版本化召回评估集和持续质量报告；
- 自动抽取、词法去重/合并和冲突记忆治理仍需加强；
- 没有精确金额成本归因；
- 本地共享状态不适合大规模分布式部署；
- 没有训练和线上反馈闭环。

### 问题十三：项目最大的技术难点是什么？

回答要点：

- 最难的是同时保证长任务的状态连续性和操作安全性；
- 工具结果不断增长，简单截断会破坏工具请求与结果的对应关系，也可能丢失已确认的关键代码信息；
- 为保持连续性，使用真实 Token 触发主动压缩、设置有边界的超限恢复，并在压缩后重注入关键状态；
- 为保证安全，不因任务变长而放宽权限，而是让所有真实动作经过确定性权限管线；
- 权限判断“能不能执行”，沙箱限制“执行后能影响多大范围”；
- 即使模型推理偏离，硬性权限和隔离边界也不能被模型直接突破。

推荐回答：

> 我认为最难的是同时保证长任务的状态连续性和操作安全性。长任务会不断产生工具结果，简单截断可能破坏工具调用与结果的对应关系，也可能丢失已经确认的关键代码信息；但为了完成任务无限放宽权限又会带来严重风险。因此我一方面实现了基于真实 Token 的主动压缩、有次数上限的超限恢复和关键状态重注入，另一方面把权限做成确定性管线，并用沙箱限制实际影响范围。这样即使模型推理出现偏差，也不会直接突破系统安全边界。

### 问题十四：为什么工具失败不直接停止任务？

回答要点：

- 失败本身也是来自真实环境的 Observation；
- 结构化错误应包含失败类型、参数问题和可恢复信息；
- 模型可以据此修改参数、切换工具、重新定位或重新规划；
- 只有硬安全拒绝、不可恢复的系统错误或全局时间边界才需要强制停止；
- 这正是 ReAct 相对固定工作流的重要价值之一。

推荐回答：

> 工具失败不是无效信息，而是环境观察。运行时会把错误结构化地返回模型，让模型修改参数、切换工具或重新规划；如果第一次失败就直接终止，Agent 就失去了根据真实反馈纠错的能力。当然，恢复仍受总时间、轮数、取消和安全规则约束。

### 问题十五：项目效果怎么样，如何避免把工程测试说成业务效果？

回答要点：

- 附件口述稿记录的一次完整测试结果是 1104 个通过、1 个跳过，覆盖 ReAct、权限、沙箱、并发、上下文、记忆、MCP、插件、子 Agent、会话和安装卸载等关键链路；
- 当前仓库静态统计有 78 个测试文件；测试数量和代码行数会随版本变化，面试前应重新运行并更新；
- 工程测试证明关键运行契约稳定，不等于真实业务任务完成率；
- 正式业务效果仍需版本化任务集、自动验收和跨版本对照；
- 重点指标包括任务成功率、P95 延迟、平均 ReAct 轮数、单成功任务成本、无效工具调用率和权限误判率；
- 线上失败轨迹应沉淀为回归样本。

推荐回答：

> 当前的单元和集成测试能够证明关键运行契约比较稳定，但我会明确区分工程正确性和业务效果。附件记录的一次完整测试是 1104 个通过、1 个跳过；真实任务成功率、成本和延迟仍需要固定版本的业务任务集验证。下一步应建立自动验收，持续统计成功率、P95 延迟、平均 ReAct 轮数、单成功任务成本、无效工具调用率和权限误判率，并把失败轨迹转成回归样本。

### 5—8 分钟完整项目陈述：定位、三大问题、质量、收获与不足

> 我主导开发了一个叫 Polaris 的智能体运行系统。它是基于 Python 自主实现的 ReAct Agent，主要面向代码仓库分析、代码修改、测试执行，以及其他需要真实工具调用的复杂任务。
>
> 这个项目的出发点是：一个真正可用的 Agent 不能只是让大模型调用一次函数，还需要解决长任务中的规划、工具编排、权限安全、上下文管理、失败恢复和运行审计。因此我没有直接依赖 LangChain 或 AutoGen，而是自己实现核心运行时，以便控制每一层的行为和安全边界。当然，这并不是否定现有框架；Provider、Tool 和 MCP 都采用接口化设计，后续仍然可以与现有生态集成。
>
> 系统的核心链路是：用户提出目标后，系统先加载项目上下文、会话状态和相关长期记忆，然后进入 ReAct 循环。模型既可以直接回答，也可以生成结构化工具调用。工具执行结果无论成功还是失败，都会作为环境观察重新交给模型，由模型根据真实结果继续决策。当模型不再请求工具时，任务自然结束；系统同时通过最大运行时间、可选最大轮数、停止阶段继续次数、上下文恢复次数和用户取消信号防止无限循环。
>
> 我在项目中重点解决了三个问题。第一个问题是工具执行的工程化。我把工具抽象成带 Schema、权限检查、并发语义和生命周期的执行单元，而不是简单的 Python 函数集合。目前系统支持文件读写、Shell、测试、Web、MCP、LSP、Notebook、Git Worktree、定时任务、Skill、插件和子 Agent 等能力。
>
> 模型一次可能生成多个工具调用，因此执行器会分析工具声明的读写资源。互不冲突的操作使用 `asyncio.gather` 并行执行；访问同一文件或共享状态的操作则分成不同执行波次串行执行。工具失败不会直接中断任务，而是返回结构化失败结果，让模型修正参数、切换工具或重新规划。为了控制上下文成本，常用工具在启动时直接暴露，LSP、Notebook、Worktree、Scheduler、Config 和 MCP Resource 等低频能力通过工具搜索按需激活。当前 MCP 服务器提供的业务 Tool 仍由 Adapter 直接注册，后续可以进一步引入 Schema 延迟加载。
>
> 第二个问题是 Agent 的安全边界。我的设计原则是不能让模型自己决定自己是否安全。每次真实工具调用都要经过确定性的权限管线，包括参数校验、管理员策略、显式 `deny` / `ask` 规则、工作区和符号链接越界检查、敏感文件保护、网络域名和 SSRF 检查、工具自己的参数级权限判断，以及最终的人工审批或自动分类。
>
> 系统提供 `default`、`acceptedits`、`plan`、`auto`、`dontask` 和 `bypass` 六种规范权限模式，同时兼容 `acceptEdits`、`dontAsk` 等输入别名。其中 `plan` 是严格只读模式，Agent 只能调查和生成计划；计划经过人工批准后才恢复执行权限。即使使用 `bypass` 或自动分类器，也不能覆盖管理员拒绝、敏感路径和其他硬性安全规则。
>
> 权限之外还有操作系统级沙箱，可以通过容器或平台原生后端限制文件、网络和进程范围。权限负责判断“能不能执行”，沙箱负责限制“执行后能影响多大范围”。所有权限决定都会进入脱敏审计日志，子 Agent 的权限也不能超过父 Agent。
>
> 第三个问题是长任务的上下文和记忆。短期上下文方面，我根据模型返回的真实 Token 使用量触发主动压缩，而不是只按字符数估算。压缩时保留用户目标、任务计划、关键决策、最近工具观察，以及工具请求与结果之间的对应关系。如果模型服务仍然返回上下文超限，系统会进行有次数上限的强制压缩和完整轮次裁剪，避免无限恢复循环。
>
> 长期记忆方面，我采用 Markdown 作为权威数据源，SQLite 和向量索引都是可以重建的派生数据。检索链路包含精确匹配、BM25、BGE-M3 向量检索、加权 RRF 融合和 BGE Reranker。小规模数据使用精确向量扫描，规模超过阈值后使用 USearch HNSW 召回，再用原始 FP32 向量精确重算。中文使用 CJK bi-gram 和 tri-gram，因此可以处理中文词法召回。模型或索引不可用时，系统会降级到 BM25 或全量 Unicode 词法扫描，记忆故障不会拖垮 Agent 主任务。
>
> 除此之外，项目还支持一次性子 Agent 和显式团队协作。子任务可以并行执行，但共享模型并发、速率和总时间预算；可写任务可以使用独立 Git Worktree 隔离，减少并行修改冲突。系统还实现了流式交互、运行中消息队列、中断和后台任务、会话恢复、插件热重载，以及 Windows、Linux、macOS 的安装和健康检查。
>
> 工程质量方面，附件口述稿记录的一次版本口径是约 3.2 万行核心 Python 代码、78 个测试文件，完整测试结果为 1104 个通过、1 个跳过。当前仓库静态统计已经约为 3.66 万行 `agent_core` Python 代码、测试文件仍为 78 个，因此代码规模和测试结果在面试前需要重新核对。测试覆盖 ReAct 循环、权限决策、沙箱、工具并发、上下文压缩、记忆检索、MCP、插件、子 Agent、会话恢复和安装卸载等关键链路。
>
> 通过这个项目，我最大的收获是：Agent 开发的核心并不只是 Prompt，而是把不确定的大模型决策放进一个确定性的运行系统里。模型决定下一步做什么，运行时决定怎样调度和恢复，安全系统决定是否允许执行。这三个决策层必须分开，Agent 才能真正做到可控、可测试和可审计。
>
> 当前项目最大的不足是还缺少基于真实业务任务集的正式评估平台。现有单元和集成测试主要证明工程行为正确，但不能完全代表真实任务完成率。下一步我会建立版本化任务集和自动验收，持续统计任务成功率、P95 延迟、平均 ReAct 轮数、单个成功任务成本、无效工具调用率和权限误判率，并把线上失败轨迹沉淀成回归样本。

这份长稿覆盖“为什么做、怎样运行、解决什么难题、目前效果、核心认识和下一步”。面试官在中途追问时，可以直接切换到本手册对应的工具、安全、记忆、多智能体或评估章节，不必坚持把长稿逐字讲完。

### 90 秒项目介绍

> 我做的 Polaris 是一个自主实现的 Python ReAct 智能体运行系统。它的目标不是只完成一次工具调用，而是让智能体可以长期、安全、可恢复地处理真实代码任务。
>
> 主循环把模型推理、结构化工具行动和环境反馈连接起来。模型每次看到文件、命令或测试结果后重新决策，没有后续工具行动时自然结束。复杂任务可以维护动态任务清单；高风险任务可以先进入严格只读的计划模式，形成计划并经过人工批准后再执行。
>
> 工具侧包含参数检查、权限判断、敏感路径保护、沙箱、资源冲突分析和安全并发。上下文侧使用真实令牌统计触发主动压缩，并在服务端拒绝超长请求时执行有边界的多阶段恢复。
>
> 系统还支持以主题 Markdown 为权威数据的跨会话长期记忆，检索链包含 Exact、BM25、BGE-M3 Dense、RRF 和 BGE 重排，并把命中的完整片段作为不可信历史上下文注入。系统同时支持一次性子智能体和带任务与消息的团队协作；所有智能体共享模型并发、请求速率和总时间，子智能体也不会获得超过父智能体的权限。
>
> 每次运行都会记录模型、工具、权限、压缩和最终结果，支持会话恢复和轨迹回放。当前最需要补强的是正式业务评估平台、记忆召回与抽取的持续评估、冲突治理和精确成本归因。

### 项目最大技术难点

> 我认为最难的不是接入模型，而是保证长任务中的状态连续性和安全性。长任务会不断产生工具结果，简单截断可能破坏工具行动与结果的关系，也可能丢失刚读过的关键代码。因此我把上下文管理分为正常主动压缩和服务端拒绝后的被动恢复，并限制恢复次数。压缩后还会重新注入关键文件状态。同时，任何真实动作都要经过参数级权限和沙箱，不能只依赖模型判断。

### 权限系统介绍

> 权限判断采用确定性的分层顺序。先检查参数、管理员策略、明确拒绝、计划模式、敏感路径和网络规则，再执行工具自身的参数级判断，最后才考虑会话授权、模式、自动分类或人工批准。自动分类器不能推翻硬拒绝，无人值守模式又必须具备沙箱，因此安全边界是可解释、可审计和可测试的。

### 多智能体介绍

> 系统支持一次性子智能体和显式团队两种方式。一次性子智能体适合独立调查，使用干净上下文并只返回结论；显式团队则有共享任务、成员消息和进度状态。所有成员共享模型并发、请求速率和总时间，权限不超过父智能体。可写任务还能使用独立版本控制工作区，减少并发修改冲突。

### 评估体系介绍

> 当前项目已经具备确定性测试模型、完整运行轨迹、令牌、时间、轮数和工具统计，但这些属于评估基础设施，还不是正式业务评估平台。下一步我会建立版本化任务集和自动验收，统一统计任务成功率、端到端延迟、单个成功任务成本和安全指标，并把失败轨迹自动沉淀成回归样本。

## 23. 面试问题：最有成就感的事情与复盘

面试官问我：请讲一件最让我有成就感的事情，你是怎么将这件事做到很好的程度。假如回过头来，让你再看一下这个事情，你觉得哪些方向还可以改进，请问我该如何回答？

我最有成就感的一件事，是作为学生第一负责人，参与并推进高速光电 AI 推理系统项目。

这个项目希望利用光子芯片“传输即计算”的特点，减少传统电学芯片中数据搬运带来的延时和能耗。项目涉及**人工智能算法、光学器件、硬件系统和加工工艺**等多个方向，而我原本的研究方向主要是 **Agent 开发和大模型算法**，光学硬件和器件工艺并不是我的专业背景。

因此，这个项目对我来说最大的挑战，不只是完成自己的算法任务，而是作为第一负责人，怎样推动一个跨学科系统真正运行起来。

在我的本职工作方面，我根据芯片的物理结构设计了物理先验驱动的 AI 模型，通过训练优化得到芯片中不同器件的权重参数，并将神经网络参数映射到实际的光学器件上。算法模型不能只追求理想环境下的准确率，还必须考虑器件的物理约束、噪声以及可实现性，所以我需要在模型性能和硬件落地之间不断做平衡。

但在项目推进过程中，我们发现很多问题并不能简单地区分为“软件问题”或者“硬件问题”。例如，实验结果出现偏差时，原因可能来自模型训练，也可能来自器件误差、调制精度或者系统连接方式。如果团队成员只关注自己的模块，问题就很难被定位。

为了解决这个问题，我主要做了三件事。

第一，我快速补充光学器件和系统方面的基础知识。我的目标并不是替代硬件和工艺方向的同学，而是理解不同器件的功能、输入输出关系和关键限制，使我能够把算法语言转化为硬件同学能够执行的参数和实验要求。

第二，我把整个系统拆解为算法训练、参数映射、器件调制、系统测试和结果验证等环节，并梳理各个模块之间的接口。当实验结果不符合预期时，我们不再依靠反复试错，而是逐层检查模型输出、参数映射和硬件响应，从而更快定位问题。

第三，我推动团队采用数据闭环的方式解决问题。每次硬件实验得到结果后，我们都会将误差反馈到模型和参数优化过程中，再进行下一轮验证。通过这种软硬件协同迭代，我们逐步完成了调制器、微环、多模干涉仪和衍射槽等器件的系统整合。

最终，系统能效达到 525 TOPS/W，3-bit 加速计算的正确率达到 100%，MNIST 图像分类准确率达到 95%，并且基于该系统构建的生成对抗网络能够完成多个数据集的图像生成。

**这件事让我最有成就感的地方，**并不只是获得了这些指标，而是**我证明了自己能够在一个并非原有研究专长的领域中，快速建立必要的认知，完成自己的核心任务，同时推动不同专业背景的成员共同解决系统级问题。**我认为这体现了我的快速学习能力、跨学科沟通能力以及对复杂项目的推进能力。

如果现在回过头来看，我认为这个项目还有三个方面可以做得更好。

第一，**在项目初期可以更早进行系统级的风险识别**。当时我们更多是按照软件、硬件和工艺分别推进，部分接口问题是在系统联调阶段才暴露出来。如果重新开展这个项目，我会在一开始就建立软硬件接口清单，提前明确每个模块的输入输出、误差范围和验证标准，从而减少后期联调成本。

第二，**可以建立更加标准化的实验和问题记录机制**。项目过程中有些问题是通过多轮尝试才定位的，但早期的实验条件、器件状态和模型版本记录得不够结构化。如果重新做，我会建立统一的实验日志和版本管理体系，使每次结果都能够追溯，也方便团队复用已有经验。

第三，**我会更早引入阶段性的端到端验证**，而不是等各个模块相对成熟后再集中整合。比如在项目早期先构建一个性能不一定最优、但能够完整运行的小规模系统，然后逐步替换和优化各个模块。这样可以更早暴露系统瓶颈，也能够让团队成员始终围绕最终目标进行协作。

因此，我认为这个项目最终的结果是成功的，但**如果重新做一次，我会更加重视前期风险管理、过程标准化和早期端到端验证**，从而用更高效、更可复制的方式取得同样甚至更好的结果。
