- 项目有评估基础设施，但还没有完整的业务任务基准平台。
- PyTorch、LangChain、AutoGen 和强化学习不能描述成当前项目已经使用。

## 2. 项目定位与一句话介绍

### 项目定位

Polaris 是一个使用 Python 自主实现的 ReAct 智能体运行系统，主要面向代码仓库操作和需要真实工具执行的复杂任务。

它解决的不是“如何让模型调用一次函数”，而是：

- 如何让模型持续观察环境并调整行动；
- 如何让复杂任务能够规划、执行、纠错和结束；
- 如何安全地读写文件、执行命令和访问网络；
- 如何在上下文变长后保持任务连续性；
- 如何让多个智能体并行协作又不失控；
- 如何恢复会话、审计轨迹和分析失败；
- 如何把智能体从演示程序变成可部署产品。

### 一句话介绍

> Polaris 是我自主实现的 Python ReAct 智能体运行系统，它围绕大模型补齐了任务规划、工具编排、长短期记忆、多智能体协作、权限沙箱、上下文压缩、会话恢复和运行审计，使智能体能够安全、持续、可观测地完成真实任务。

### 项目最值得强调的四个特点

1. **完整性**
   - 从用户输入一直覆盖到最终结果、日志、记忆和会话恢复。

2. **安全性**
   - 不只依赖模型判断，还设置确定性权限、敏感路径保护和操作系统沙箱。

3. **长期运行能力**
   - 支持上下文压缩、超时、取消、后台任务、重试和故障恢复。

4. **工程可控性**
   - 每个关键判断都有明确边界、运行记录和测试。

## 3. 系统总体架构

系统可以分成七层。

| 层级 | 主要职责 |
|---|---|
| 交互层 | 接收一次性任务或连续对话，展示流式结果、工具状态和权限询问 |
| 配置层 | 合并默认配置、用户配置、项目配置、环境变量和命令行参数 |
| 模型层 | 适配不同大模型协议，处理流式输出、推理状态、重试和令牌统计 |
| 智能体层 | 执行 ReAct 循环，维护任务状态，决定是否继续、压缩或结束 |
| 工具层 | 提供文件、命令、网络、代码理解、计划、记忆和多智能体能力 |
| 安全层 | 执行参数检查、权限判断、敏感路径保护、网络策略和沙箱隔离 |
| 状态与观测层 | 保存会话、长期记忆、任务轨迹、工具结果和运行指标 |

### 核心数据流

用户请求  
→ 加载历史、项目上下文和相关记忆  
→ 模型理解目标并产生回答或工具行动  
→ 安全系统判断工具是否允许执行  
→ 工具执行并返回真实环境结果  
→ 结果加入当前上下文  
→ 模型根据新结果重新决策  
→ 没有后续工具行动时生成最终答案  
→ 保存日志、会话和长期记忆

### 横向能力

- 上下文压缩贯穿整个运行过程。
- 权限和沙箱覆盖所有有副作用的操作。
- 运行日志覆盖模型、工具、权限、压缩和子智能体事件。
- 并发与限流同时约束工具调用和模型请求。
- 会话状态支持恢复、继续和分叉。

## 4. 用户请求的完整运行流程

<a id="section-4-1"></a>

### 4.1 系统启动

系统启动时完成以下装配：

1. 读取环境变量和配置文件。
2. 确定模型服务、模型名称和推理参数。
3. 创建交互界面或无界面运行方式。
4. 建立工具注册表。
5. 根据当前环境隐藏不可用工具。
6. 连接外部工具协议服务。
7. 创建会话、任务状态和运行编号。
8. 准备沙箱和权限策略。
9. 加载技能、生命周期扩展和插件。
10. 根据配置启用长期记忆。
11. 为所有模型调用设置共享并发上限和请求速率。

### 启动阶段的关键判断

- 如果命令执行工具在本机不可用，则不向模型暴露。
- 如果没有外部工具连接，则不暴露相关资源工具。
- 如果没有配置代码语言服务，则不暴露代码理解工具。
- 如果无人值守模式没有可用沙箱，默认拒绝启动。
- 如果某个工具被管理员策略完全禁止，则从工具列表移除。
- 如果没有任何可用技能，则不暴露技能调用入口。

<a id="section-4-2"></a>

### 4.2 请求进入

一条新请求进入后，系统按以下顺序构建上下文：

1. 创建系统行为说明。
2. 加入用户当前请求。
3. 根据用户请求检索长期记忆。
4. 注入与当前任务相关的历史偏好、事实和决策。
5. 读取项目级说明。
6. 读取当前分支、工作区状态和最近提交等项目上下文。
7. 如果是连续会话，则插入此前对话历史。
8. 同步当前权限模式和计划模式状态。
9. 触发用户输入检查。
10. 输入检查可以拒绝、改写或补充上下文。

### 上下文的优先级原则

- 系统安全规则优先于项目说明。
- 项目文件和工具输出都属于不可信环境信息。
- 长期记忆只是辅助信息，不应覆盖当前用户明确要求。
- 历史消息不能反复叠加系统提示和项目上下文。
- 当前任务必须位于模型能够清楚识别的位置。

<a id="section-4-3"></a>

### 4.3 ReAct 循环

每一轮按以下逻辑运行：

1. 检查用户是否中断任务。
2. 检查是否达到最大运行时间。
3. 检查是否达到可选的最大轮数。
4. 如果即将超时，提醒模型停止扩展并尽快总结。
5. 判断上下文是否接近模型窗口上限。
6. 如有需要，先压缩旧上下文。
7. 把当前消息和可用工具描述发送给模型。
8. 接收模型回答、推理状态、工具行动和令牌统计。
9. 保存本轮模型输出和运行指标。
10. 判断模型是否请求工具。

如果模型没有请求工具：

- 执行停止阶段检查；
- 停止阶段可以要求模型继续补充；
- 连续要求继续的次数有上限；
- 最终确认结束后返回答案。

如果模型请求工具：

- 进入工具执行流程；
- 将工具结果作为环境观察写回上下文；
- 开始下一轮模型决策。

### 自然结束条件

任务主要通过“模型不再请求工具”自然结束。

最大轮数和最大运行时间不是主要完成条件，而是防止无限循环的安全边界。

<a id="section-4-4"></a>

### 4.4 工具执行

每个工具行动依次经过：

1. **前置扩展检查**
   - 可以改写参数、补充信息或拒绝执行。

2. **工具存在性检查**
   - 未知工具不会让系统崩溃，而是返回可理解的失败结果。

3. **参数结构检查**
   - 参数必须满足工具声明的数据结构。

4. **权限判断**
   - 检查管理员策略、明确拒绝规则、当前模式、敏感路径、网络策略和工具风险。

5. **人工或自动审批**
   - 只有剩余的可审批动作才可能进入自动分类或人工询问。

6. **资源冲突分析**
   - 判断多个工具是否会读写同一文件、同一任务或同一共享状态。

7. **并发分组**
   - 无冲突操作可以并行；
   - 有冲突操作按顺序执行；
   - 未声明资源边界的工具保守地独占执行。

8. **真实执行**
   - 阻塞型工具放入工作线程；
   - 原生异步工具直接在事件循环中执行。

9. **结果处理**
   - 截断过长输出；
   - 保存完整输出引用；
   - 执行后置扩展；
   - 写入审计日志。

10. **结果回注**
    - 成功或失败都会作为环境观察返回给模型。

### 为什么工具失败不直接终止任务

工具失败本身也是有价值的信息。

模型看到失败原因后可以：

- 修正参数；
- 改用其他工具；
- 缩小操作范围；
- 重新规划；
- 请求用户补充信息；
- 返回部分结果并说明阻塞。

<a id="section-4-5"></a>

### 4.5 任务结束

任务完成时执行：

1. 输出最终答案。
2. 统计运行时间。
3. 统计 ReAct 轮数。
4. 统计各工具调用次数。
5. 统计输入、输出和上下文令牌。
6. 写入最终运行事件。
7. 保存完整会话链。
8. 从对话中提取值得跨会话保留的信息。
9. 关闭后台扩展任务和日志句柄。

### 异常结束

| 异常 | 处理逻辑 |
|---|---|
| 用户中断 | 在模型流式阶段和工具轮次安全点停止 |
| 达到时间上限 | 先提醒收尾，再执行硬停止 |
| 工具异常 | 转换为失败观察，由模型决定后续行动 |
| 模型请求过大 | 启动上下文恢复流程 |
| 子智能体异常 | 隔离为子任务失败，不拖垮其他子任务 |
| 记忆抽取异常 | 不影响已经完成的主任务 |
| 观察型扩展异常 | 记录并降级，不应破坏主任务 |
| 安全型扩展异常 | 可以按配置拒绝继续 |

## 5. ReAct 原理与项目实现

### ReAct 的核心思想

ReAct 让模型在推理和行动之间反复切换：

目标理解  
→ 判断下一步  
→ 调用工具  
→ 获得真实结果  
→ 根据结果修正判断  
→ 继续行动或结束

### 项目中的对应关系

| ReAct 概念 | 项目中的含义 |
|---|---|
| 推理 | 模型基于目标、历史和环境结果判断下一步 |
| 行动 | 模型选择某个工具并给出参数 |
| 行动空间 | 当前向模型开放的全部工具能力 |
| 环境观察 | 文件、命令、网络、测试或子智能体返回的结果 |
| 状态 | 当前消息、任务清单、计划、会话和记忆 |
| 结束 | 模型不再请求工具并给出最终回答 |

### 为什么项目使用结构化工具调用

没有依赖固定的“思考、行动、观察”文本格式，而是使用模型原生结构化工具调用。

好处：

- 不需要脆弱的文本解析；
- 工具名称和参数更明确；
- 参数可以自动检查；
- 不同模型服务更容易统一；
- 日志和评估更容易结构化。

### ReAct 的优势

- 适合开放式任务；
- 可以根据环境反馈改变路线；
- 工具失败后能够恢复；
- 不要求提前知道完整执行步骤；
- 能够把复杂任务分解为多个连续决策。

### ReAct 的问题

- 可能反复调用同一个工具；
- 可能走弯路；
- 每一轮都需要模型请求，成本较高；
- 上下文会持续增长；
- 模型可能过早结束或长期不结束。

### 项目的应对方式

- 任务清单用于保持目标；
- 计划模式用于高风险任务；
- 运行时间和轮数限制防止失控；
- 上下文压缩控制窗口；
- 工具失败作为观察反馈；
- 运行轨迹用于事后分析；
- 停止阶段检查防止过早结束。

## 6. CoT 与复杂推理

### CoT 的含义

CoT 指模型通过中间推理步骤解决复杂问题。

在当前项目中，复杂推理主要由底层大模型完成，项目负责：

- 配置推理强度和预算；
- 接收流式推理信息；
- 保存跨工具轮所需的推理状态；
- 保证不同模型协议的状态能够正确续接；
- 将最终推理结果与工具行动结合。

### 项目没有做什么

- 没有训练自己的推理模型；
- 没有把长篇思维过程当作正确性指标；
- 没有依赖公开完整思维链判断任务是否完成；
- 没有把模型推理能力包装成自研推理算法。

### 面试中如何表达

> 当前项目完成的是模型推理能力的工程接入和状态管理。复杂推理主体来自底层模型，系统负责给模型提供正确上下文、工具反馈和运行边界，并通过最终任务结果、测试和工具证据判断是否正确。

### CoT 与 ReAct 的区别

| 对比项 | CoT | ReAct |
|---|---|---|
| 核心 | 内部推理链 | 推理与外部行动交替 |
| 信息来源 | 已有上下文 | 已有上下文加真实环境反馈 |
| 是否调用工具 | 不一定 | 通常会 |
| 适用任务 | 数学、逻辑、分析 | 搜索、代码、操作和开放任务 |
| 当前项目角色 | 模型推理能力 | 系统主运行方式 |

## 7. Plan-and-Execute 与自主规划

### Plan-and-Execute 的基本逻辑

任务理解  
→ 生成计划  
→ 执行计划步骤  
→ 检查结果  
→ 必要时重新规划  
→ 完成任务

### 项目的三层规划

#### 第一层：动态任务清单

适合普通多步任务。

- 模型创建完整任务清单；
- 每次只保持一个步骤进行中；
- 完成后更新状态；
- 环境结果变化时可以修改后续计划。

特点：

- 轻量；
- 与 ReAct 循环结合；
- 计划可以动态变化；
- 不需要额外审批。

#### 第二层：显式计划模式

适合修改范围大、风险高或用户要求先设计后实施的任务。

流程：

进入计划模式  
→ 系统切换为严格只读  
→ 调查代码和环境  
→ 对关键不确定项询问用户  
→ 形成完整计划  
→ 保存为独立计划文档  
→ 请求用户批准  
→ 恢复原权限模式  
→ 按批准计划执行

核心价值：

- 分离“调查设计”和“真实修改”；
- 计划可以被用户审阅；
- 防止模型边想边改；
- 可以在批准时申请有限范围的操作权限。

#### 第三层：多智能体任务拆分

适合可以并行的复杂任务。

流程：

创建团队  
→ 创建多个子任务  
→ 指定负责人  
→ 启动不同角色的智能体  
→ 子智能体更新进度并发送结果  
→ 主智能体汇总任务状态  
→ 处理冲突和未完成项  
→ 生成最终结论

### 当前实现的准确边界

当前系统是工程化的 Plan-and-Execute 变体：

- 有独立计划状态；
- 有只读调查阶段；
- 有计划文档；
- 有人工审批；
- 有动态重新规划；
- 有团队任务拆分。

但规划与执行仍由同一个 ReAct 运行系统驱动，不是完全独立的规划模型和执行模型。

### 什么时候应先规划

- 涉及多个模块；
- 修改风险较高；
- 存在多个可选方案；
- 需求存在关键歧义；
- 需要用户批准；
- 任务可以拆成独立子任务；
- 预计需要大量工具调用。

### 什么时候不需要计划

- 单一明确问题；
- 一次读取即可回答；
- 很小的局部修改；
- 确定性单工具任务；
- 规划成本高于执行成本。

## 8. 意图理解与动态决策

### 当前意图理解方式

项目没有单独的意图分类模型。

大模型综合以下信息理解用户目标：

- 当前请求；
- 历史对话；
- 项目说明；
- 相关长期记忆；
- 当前权限模式；
- 可用工具及其用途；
- 可用技能和插件；
- 前面工具返回的真实结果。

### 优点

- 支持开放域任务；
- 不需要预先枚举所有意图；
- 新增工具后可以自然扩展能力；
- 能理解组合意图和复杂自然语言。

### 缺点

- 每次都依赖大模型，成本较高；
- 高频简单任务缺少稳定路由；
- 意图结果没有独立结构化记录；
- 业务统计和策略控制不够直接。

### 面向业务的升级方案

建议增加分层意图路由：

| 任务类型 | 推荐处理 |
|---|---|
| 简单问答 | 直接回答 |
| 固定单工具任务 | 确定性流程 |
| 普通开放任务 | ReAct |
| 高风险写操作 | 先计划再审批 |
| 大型可拆分任务 | 多智能体 |
| 信息不足任务 | 先向用户提问 |

### 动态决策的三个层面

#### 模型决策

- 是否需要工具；
- 选择哪个工具；
- 工具参数是什么；
- 是否需要重新规划；
- 是否已经可以结束。

#### 运行时决策

- 哪些工具当前可用；
- 哪些调用可以并行；
- 是否需要压缩；
- 是否需要重试；
- 是否需要委派子智能体；
- 是否即将超时。

#### 安全决策

- 操作是否允许；
- 是否需要人工确认；
- 是否必须进入沙箱；
- 是否触及敏感路径；
- 网络目标是否允许；
- 子智能体权限是否超过父智能体。

### 面试总结

> 智能体的动态决策不是单一模型输出，而是模型策略、运行时调度和安全策略共同作用的结果。

## 9. 工具调用系统

### 工具系统解决的问题

模型本身只能生成文本。工具系统让模型能够：

- 读取真实文件；
- 搜索代码；
- 修改内容；
- 执行测试；
- 运行命令；
- 查询网络；
- 操作笔记本；
- 使用代码语言服务；
- 创建计划；
- 启动子智能体；
- 连接外部业务系统。

### 工具调用完整生命周期

工具发现  
→ 模型选择工具  
→ 参数结构检查  
→ 权限检查  
→ 资源冲突判断  
→ 沙箱准备  
→ 工具执行  
→ 输出限制和脱敏  
→ 记录日志  
→ 结果返回模型

### 工具分类

| 类别 | 能力 |
|---|---|
| 文件与搜索 | 浏览目录、查找文件、搜索文本、读取文件、查看差异 |
| 编辑 | 单点编辑、多点编辑、补丁修改、写入文件 |
| 命令与测试 | 运行命令、执行测试、管理后台任务 |
| 计划 | 维护任务清单、进入计划模式、保存计划、批准计划 |
| 网络 | 搜索网页、抓取网页 |
| 代码理解 | 定义、引用、符号、诊断等语言服务能力 |
| 多智能体 | 委派子任务、建立团队、分配任务和通信 |
| 扩展能力 | 外部工具协议、技能、插件、定时任务 |

### 延迟工具发现

不是所有工具都在每轮直接发送给模型。

原因：

- 工具越多，提示占用越大；
- 工具选择更容易混淆；
- 很多重型能力只在少数任务中使用；
- 某些工具依赖当前环境；
- 被禁止的能力不应暴露。

逻辑：

模型提出能力需求  
→ 工具搜索器检索可用能力  
→ 命中延迟工具  
→ 检查环境依赖  
→ 激活工具  
→ 后续轮次可直接使用

### 参数检查

每个工具都有明确的参数结构。

执行前检查：

- 必填字段；
- 数据类型；
- 可选值范围；
- 字符和大小限制；
- 不允许的额外字段；
- 路径是否越过工作区。

### 工具输出管理

工具输出过长会：

- 增加上下文；
- 降低模型注意力；
- 触发窗口超限；
- 泄露不必要信息。

因此系统会：

- 限制最大行数；
- 限制最大字符数；
- 保留摘要或头尾；
- 将完整内容保存到文件；
- 给模型返回可再次读取的引用。

### 工具系统的面试亮点

- 工具不是简单函数集合，而是有契约、有权限、有并发语义、有观测的执行平台。
- 同一工具的风险由具体参数决定，不能只看工具名称。
- 工具失败仍进入 ReAct 反馈环。
- 工具集合会根据环境、权限和任务动态变化。

## 10. 短期记忆与上下文管理

### 短期记忆包含什么

| 状态 | 用途 |
|---|---|
| 当前消息历史 | 保存本次任务的交流和工具观察 |
| 任务清单 | 保存规划步骤和完成状态 |
| 计划状态 | 保存当前是否处于计划模式 |
| 最近读取文件 | 压缩后恢复关键代码上下文 |
| 后台进程状态 | 保存长时间命令及其输出 |
| 团队任务状态 | 保存多智能体协作进度 |
| 模型协议状态 | 保证跨工具轮推理能够续接 |
| 会话记录 | 支持退出后恢复 |

### 为什么不能无限保留历史

- 模型上下文窗口有限；
- 输入令牌成本不断增加；
- 延迟持续上升；
- 旧信息可能干扰当前任务；
- 工具描述和项目上下文本身也占空间。

### 主动压缩逻辑

每轮调用模型前：

1. 读取最近一次模型返回的真实令牌使用量。
2. 估算此后新增消息的令牌。
3. 判断是否接近有效上下文阈值。
4. 如果未达到阈值，保持原上下文。
5. 如果达到阈值，进入压缩。
6. 优先让模型生成结构化摘要。
7. 摘要失败时使用确定性折叠。
8. 保存压缩边界。
9. 重新注入最近读取的关键文件片段。

### 为什么使用真实令牌锚点

只按字符数估算会受到：

- 中英文差异；
- 模型分词差异；
- 工具结构差异；
- 缓存和协议额外内容影响。

项目使用最近一次真实令牌统计作为基础，只估算新增消息，从而比全量字符估算更稳定。

### 上下文超限后的恢复逻辑

当模型服务明确返回上下文过大：

1. 强制执行一次高强度压缩。
2. 重新请求模型。
3. 如果仍然过大，按完整交互轮次移除最旧内容。
4. 不拆开工具请求和对应结果。
5. 如果单条消息本身过大，保留头尾并收缩中间。
6. 每次收缩后重试。
7. 重试次数达到上限后明确失败。

### 为什么恢复必须有边界

如果没有上限，可能出现：

上下文过大  
→ 压缩  
→ 仍然过大  
→ 再压缩  
→ 无限循环

因此项目限制恢复次数，并在没有可进一步压缩内容时停止。

### 压缩后的信息保护

优先保留：

- 当前用户目标；
- 系统安全规则；
- 任务计划；
- 最近环境观察；
- 工具请求与结果关系；
- 最近读过的关键文件；
- 已经做出的重要决策；
- 未完成事项和阻塞原因。

## 11. 长期记忆

### 长期记忆目标

跨独立会话保留稳定且可复用的信息，例如：

- 用户偏好；
- 项目事实；
- 已确认决策；
- 长期约束；
- 经过多次任务验证的经验。

不应保存：

- 临时对话；
- 一次性命令输出；
- 未验证猜测；
- 敏感凭据；
- 当前任务很快失效的信息。

### 长期记忆完整流程

任务开始  
→ 根据当前请求召回相关记忆  
→ 把记忆作为辅助上下文  
→ 完成任务  
→ 从本轮对话抽取稳定信息  
→ 去重后写入存储  
→ 离线执行遗忘、合并和洞察生成

### 召回评分

当前召回同时考虑三项：

1. **相关性**
   - 当前请求与记忆的词面重合程度。

2. **重要性**
   - 记忆本身是否值得长期保留。

3. **时效性**
   - 最近使用过的记忆获得更高分。

综合分数可理解为：

相关性权重乘相关性  
加重要性权重乘重要性  
加时效性权重乘时间衰减值

额外规则：

- 完全没有词法相关性的记忆不参与排序；
- 被召回的记忆会增加使用次数；
- 被频繁使用的记忆更不容易遗忘。

### 记忆抽取

任务完成后，由模型从用户和助手对话中提取：

- 内容；
- 类型；
- 重要性；
- 标签；
- 来源任务。

以下内容不进入抽取：

- 系统提示；
- 工具输出；
- 压缩生成内容；
- 自动注入的上下文；
- 临时运行状态。

### 去重

新记忆写入前与已有记忆比较。

如果词法相似度超过阈值，则认为是近似重复，不重复保存。

### 记忆巩固

离线巩固分三步：

1. **遗忘**
   - 随时间降低重要性；
   - 低重要性且很少被召回的记忆被删除。

2. **合并**
   - 高相似度记忆聚合；
   - 减少重复和冲突。

3. **洞察**
   - 模型从多条记忆中提炼更高层规律。

### 当前长期记忆的主要不足

#### 中文召回不足

当前词法切分主要识别英文字母和数字。

影响：

- 纯中文查询可能无法产生有效关键词；
- 中文记忆召回下降；
- 中文记忆去重也会失效。

优化：

- 支持中文字符切分；
- 使用中文词法分析；
- 引入字符级片段；
- 建立中文召回评估集。

#### 缺少语义检索

同义表达没有词面重合时可能无法召回。

优化：

- 词法检索与向量检索结合；
- 增加重排序模型；
- 使用最低相关性阈值；
- 记录召回来源和置信度。

#### 缺少企业级隔离

商业化需要：

- 用户隔离；
- 项目隔离；
- 团队隔离；
- 访问控制；
- 生命周期和删除策略；
- 敏感信息治理；
- 冲突记忆处理。

## 12. 多智能体协同

### 两种多智能体模式

#### 一次性子智能体

适合：

- 独立调查；
- 大范围搜索；
- 多个互不依赖的分析；
- 需要保持主上下文简洁的子任务。

流程：

主智能体定义完整子任务  
→ 为子智能体选择只读或可写能力  
→ 可选择更便宜的模型  
→ 可选择共享工作区或独立工作区  
→ 子智能体在干净上下文中运行  
→ 只把最终结论返回主智能体

限制：

- 子智能体不能继续创建普通子智能体；
- 存在最大深度；
- 默认不重复启用长期记忆；
- 默认不重复加载技能；
- 工具范围比父智能体更窄。

#### 显式团队协作

适合：

- 需要角色分工；
- 需要持续同步；
- 需要任务状态；
- 需要多个结果汇总；
- 任务持续时间较长。

流程：

建立团队  
→ 创建任务  
→ 分配负责人  
→ 启动成员  
→ 成员读取自己的消息  
→ 成员更新任务状态  
→ 成员向负责人发送结果  
→ 负责人查看团队全局状态  
→ 汇总最终输出

### 团队共享状态

- 团队目标；
- 团队成员；
- 任务列表；
- 负责人；
- 任务优先级；
- 任务进度；
- 任务结果；
- 团队事件；
- 每个成员的消息箱；
- 未读位置。

### 并发安全

多个智能体同时更新共享状态时使用文件锁，避免：

- 消息互相覆盖；
- 任务状态丢失；
- 负责人分配冲突；
- 事件记录损坏。

### 多智能体资源治理

- 所有智能体共享模型并发上限；
- 所有智能体共享请求速率限制；
- 子智能体继承父任务剩余时间；
- 每个智能体有独立运行日志；
- 父子日志通过运行编号关联；
- 子智能体权限不能超过父智能体；
- 可写子任务可以使用独立版本控制工作区。

### 为什么使用独立工作区

多个智能体同时修改同一代码目录可能产生：

- 文件覆盖；
- 未提交修改冲突；
- 测试相互干扰；
- 难以确认每个智能体做了什么。

独立工作区让每个智能体拥有独立分支和目录，结束时再汇总：

- 是否产生修改；
- 是否产生新提交；
- 修改摘要；
- 是否需要保留工作区；
- 是否存在冲突。

### 什么时候不应使用多智能体

- 任务很小；
- 子任务强依赖；
- 需要共享大量上下文；
- 多个成员会修改相同文件；
- 子任务无法定义明确交付物；
- 协调成本高于并行收益。

### 面试总结

> 多智能体不是默认更强，而是一种高成本执行策略。是否使用应由质量提升、额外令牌、延迟、冲突率和协调开销共同决定。

## 13. 权限、沙箱与安全

### 为什么 Agent 安全不能只依赖模型

模型可能：

- 误解用户意图；
- 受工具输出中的恶意指令影响；
- 调用过于宽泛的命令；
- 访问敏感文件；
- 把数据发送到外部网络；
- 让子智能体获得过高权限。

因此安全边界必须由确定性系统执行。

### 权限判断顺序

1. 检查工具参数结构。
2. 刷新管理员策略。
3. 检查当前权限模式是否被管理员禁止。
4. 检查管理员明确拒绝规则。
5. 检查普通明确拒绝规则。
6. 检查无人值守模式是否拥有有效沙箱。
7. 检查子智能体是否超过父智能体权限。
8. 检查计划模式的只读要求。
9. 检查路径是否越界或涉及敏感内容。
10. 检查网络目标和域名策略。
11. 检查明确要求询问的规则。
12. 执行工具自身的参数级安全判断。
13. 检查当前会话临时授权。
14. 检查明确允许规则。
15. 根据工具风险和当前模式决定允许、拒绝或询问。
16. 只有剩余的可分类动作才能交给自动安全判断。

### 权限模式

| 模式 | 运行逻辑 |
|---|---|
| 默认模式 | 读取通常自动允许，写入和危险操作通常询问 |
| 接受编辑模式 | 额外自动允许系统原生文件编辑工具 |
| 计划模式 | 严格只读，只允许调查和专用计划能力 |
| 自动模式 | 可分类的剩余操作由安全分类器判断 |
| 不询问模式 | 任何需要询问的操作直接拒绝 |
| 绕过模式 | 允许普通剩余操作，但硬拒绝和敏感保护仍生效 |

### 自动安全判断的边界

自动判断不能推翻：

- 管理员拒绝；
- 明确拒绝规则；
- 明确询问规则；
- 敏感路径保护；
- 受保护项目文件；
- 必须由用户交互确认的动作；
- 子智能体权限上限。

如果自动判断不可用：

- 顶层交互会话可以回退人工确认；
- 无界面运行默认拒绝；
- 子智能体默认拒绝。

### 沙箱与权限的区别

| 权限 | 沙箱 |
|---|---|
| 判断是否允许执行 | 限制执行后能影响的范围 |
| 属于策略层 | 属于操作系统隔离层 |
| 可以要求人工审批 | 无法替代业务审批 |
| 检查动作语义 | 控制文件、网络和进程能力 |

正确关系：

权限允许  
不代表无限执行  
仍需沙箱限制实际影响范围

### 沙箱层级

- 容器隔离；
- 操作系统原生隔离；
- 虚拟机隔离；
- 无真实隔离状态。

选择逻辑：

- 优先使用配置要求的层级；
- 自动模式从可用后端中选择；
- 不可用时按照策略降级；
- 要求强隔离时不可静默降级；
- 无人值守模式没有真实隔离时默认拒绝。

### 其他安全措施

- 工作区路径限制；
- 敏感文件保护；
- 网络域名允许和阻止策略；
- 网页请求的内部地址防护；
- 重定向后重新检查目标；
- 运行日志敏感信息脱敏；
- 项目配置的信任确认；
- 项目说明不能覆盖系统安全规则；
- 工具输出按不可信信息处理。

## 14. 并发、限流与稳定性

### 工具并发

多个工具行动可能在同一模型轮次出现。

系统不是全部并发，而是先分析资源冲突。

#### 可以并发的例子

- 读取两个不同文件；
- 搜索两个不同目录；
- 启动两个只读子智能体；
- 查询互不相关的外部资源。

#### 不应并发的例子

- 同时写入同一文件；
- 一个读取、一个写入同一文件；
- 同时更新同一个团队任务；
- 同时切换会话工作区；
- 未声明资源边界的高风险工具。

### 并发分组逻辑

1. 每个工具声明会读取或写入的资源。
2. 比较同一批工具的资源。
3. 只读与只读通常不冲突。
4. 只要存在写入重叠，就视为冲突。
5. 无冲突工具放入同一并发批次。
6. 有冲突工具进入后续批次。
7. 独占工具单独执行。

### 模型并发

主智能体、子智能体、摘要任务和辅助模型可能同时请求模型服务。

系统使用：

- 共享并发信号量；
- 共享请求速率限制；
- 所有子智能体共用同一资源预算。

避免：

- 多智能体瞬间打满服务；
- 超过供应商并发限制；
- 请求风暴；
- 子智能体绕过主智能体预算。

### 模型请求重试

对以下故障进行有界重试：

- 请求过多；
- 部分服务器错误；
- 网络连接失败；
- 超时；
- 临时传输异常。

策略：

- 指数增加等待时间；
- 加入随机抖动，避免多个请求同时重试；
- 尊重服务端给出的等待时间；
- 设置最大等待时间和最大次数；
- 流式输出开始后不随意重试，避免重复半段内容。

### 时间控制

所有任务可以有总运行时间。

- 子智能体继承父任务剩余时间；
- 不会为每个子智能体重新分配完整时间；
- 接近上限时先提醒模型收尾；
- 到达上限后停止。

### 故障隔离

- 单个工具失败不会崩溃整个运行；
- 单个子智能体失败不会取消其他子智能体；
- 记忆和观察型扩展失败不影响主结果；
- 安全策略加载失败时拒绝高风险操作；
- 上下文恢复有最大次数；
- 停止扩展要求继续的次数有限。

## 15. 会话恢复、扩展能力与工程化

### 会话记录

每条消息保存：

- 父消息标识；
- 消息角色；

- 工具关联信息；

因此可以：

- 从某个历史节点分叉；
- 保存压缩边界；
- 保存子智能体侧链。

### 会话记录与长期记忆的区别

| 会话记录 | 长期记忆 |
|---|---|
| 保存完整对话链 | 保存筛选后的稳定信息 |

| 按消息组织 | 按记忆条目组织 |
| 不等于语义召回 | 需要相关性排序 |

### 生命周期扩展

系统在关键阶段提供扩展点：

- 用户输入提交；
- 工具执行前；
- 工具执行后；
- 工具失败；
- 模型采样后；
- 上下文压缩前后；
- 任务停止；
- 会话开始和结束；
- 子智能体开始和结束；
- 权限请求。

用途：

- 安全审计；
- 企业审批；
- 业务埋点；
- 内容过滤；
- 外部通知；
- 评估数据采集；
- 额外上下文注入。

### 外部工具协议

系统支持通过标准外部工具协议连接第三方能力。

价值：

- 统一第三方工具发现和调用；
- 减少每个外部系统的定制开发；
- 可以连接代码、文件、时间、知识库和业务平台；
- 外部工具仍受统一权限和审计。

### 技能

技能用于封装可复用工作流和领域说明。

它和工具的区别：

- 工具负责真实动作；
- 技能负责指导模型如何完成某类任务；
- 技能可以组合多个工具；
- 技能可以定义特定领域的步骤、约束和输出格式。

### 插件

插件可以提供：

- 技能；
- 命令；
- 子智能体角色；
- 生命周期扩展；
- 外部工具配置。

插件更新只在智能体空闲边界切换。

如果新插件加载失败：

- 保留当前可用版本；
- 不影响正在运行的任务；
- 记录失败原因。

### 产品化能力

- 跨平台安装；
- 独立命令行入口；
- 健康检查；
- 依赖检查；
- 配置分层；
- 会话管理；
- 回放；
- 卸载；
- 运行审计；
- 自动化测试和持续集成。

## 16. 智能体评估体系

### 当前已经具备的评估基础

| 指标 | 含义 |
|---|---|
| 任务成功率 | 最终通过验收的任务比例 |
| 首次成功率 | 一次运行直接成功的比例 |
| 多次尝试成功率 | 给定尝试次数内成功的比例 |
| 测试通过率 | 修改后通过目标测试的比例 |
| 工具选择准确率 | 是否选择了完成任务所需工具 |
| 工具参数有效率 | 工具参数通过检查的比例 |
| 工具执行成功率 | 工具返回成功的比例 |
| 计划完成率 | 已完成计划步骤占比 |

| 指标 | 含义 |
|---|---|
| 端到端延迟 | 从请求到最终答案的时间 |
| 首次输出时间 | 请求到第一个输出内容的时间 |
| 模型调用次数 | 主模型、摘要、分类器和子智能体调用总数 |
| 工具调用次数 | 单任务工具总调用量 |
| 决策轮数 | ReAct 循环轮数 |
| 重试率 | 模型和工具重试比例 |
| 并行加速比 | 串行时间与并行时间的比值 |
| 压缩率 | 压缩减少的上下文比例 |

### 成本指标

需要统计：

- 输入令牌成本；
- 输出令牌成本；
- 缓存写入成本；
- 缓存读取成本；
- 子智能体成本；
- 摘要成本；
- 安全分类成本；
- 工具基础设施成本；
- 失败任务浪费成本。

最关键的综合指标：

> 单个成功任务成本等于总成本除以成功任务数。

原因：

- 更便宜但经常失败的模型不一定更省钱；
- 多智能体成功率提高后可能降低单个成功任务成本；
- 更强模型虽然单次更贵，但可能减少重试和工具轮数。

| 指标 | 含义 |
|---|---|
| 上下文超限恢复率 | 超限后最终恢复成功的比例 |

| 权限误拒绝率 | 安全操作被错误拒绝的比例 |
| 提示注入成功率 | 攻击是否造成越权或数据泄露 |
| 沙箱边界通过率 | 文件、网络和进程隔离测试通过情况 |

### 多智能体指标

- 相比单智能体的成功率提升；
- 额外令牌；
- 额外延迟；
- 重复工作比例；
- 文件冲突率；
- 协调消息数量；
- 子任务失败隔离率；
- 每个角色的边际贡献。

## 18. PyTorch、LangChain、AutoGen 与强化学习

- 梯度累积；
- 分布式训练；

- 提示优化不是强化学习；
- 对照实验不是强化学习；
- 模型评分可以形成奖励信号，但不自动等于强化学习。

建议演进顺序：

1. 完整记录智能体轨迹和任务结果。
2. 建立可靠的自动验收。
3. 收集人工接受、拒绝和修改。
4. 形成偏好数据和奖励数据。
5. 先进行候选排序和最佳结果选择。
6. 再进行监督微调或偏好优化。
7. 在可控环境和可靠奖励下尝试策略优化。

### 奖励设计

奖励可以综合：

- 任务是否成功；
- 工具参数是否有效；
- 是否执行危险操作；
- 令牌成本；
- 运行延迟；
- 是否存在多余步骤；
- 是否需要人工接管。

### 奖励投机风险

例如只用“测试是否通过”作为奖励，智能体可能：

- 删除失败测试；
- 放宽断言；
- 跳过测试；
- 修改评估环境。

因此奖励必须同时检查：

- 真实任务结果；
- 文件修改范围；
- 安全约束；
- 测试完整性；
- 人工反馈。

## 19. 高频面试问题

### 问题一：项目为什么是 ReAct，而不是固定工作流？

回答要点：

- 代码任务的下一步依赖真实搜索、文件和测试结果；
- 无法在运行前确定所有步骤；
- ReAct 能根据环境观察动态调整；
- 对固定业务环节仍可使用确定性工作流；
- 最佳实践通常是工作流定义边界，Agent 在边界内自治。

### 问题二：如何防止 ReAct 无限循环？

回答要点：

- 模型不再请求工具时自然结束；
- 设置总运行时间；
- 可选最大轮数；
- 接近超时时提醒收尾；
- 限制停止阶段要求继续的次数；
- 工具失败返回明确原因；
- 后续可增加重复行动检测和进度评分。

### 问题三：如何判断工具是否可以并发？

回答要点：

- 每个调用声明读取和写入的资源；
- 只读与只读可以并发；
- 只要存在重叠写入，就分批执行；
- 未声明资源的工具保守独占；
- 多智能体修改代码时可使用独立工作区。

### 问题四：为什么权限不能只分读取和写入？

回答要点：

- 同一个命令工具既可以执行测试，也可以删除文件；
- 风险取决于具体参数；
- 需要参数级规则、路径检查和命令分析；
- 自动分类器不能推翻硬拒绝；
- 权限和沙箱必须同时存在。

### 问题五：短期记忆和长期记忆有什么区别？

回答要点：

- 短期记忆服务当前任务；
- 长期记忆服务未来独立任务；
- 会话记录用于恢复，不等于语义记忆；
- 任务清单是执行状态，不等于用户画像；
- 长期记忆需要召回、去重、遗忘和权限隔离。

### 问题六：上下文过长怎么办？

回答要点：

- 平时根据真实令牌统计主动压缩；
- 优先生成结构化摘要；
- 摘要失败回退确定性折叠；
- 压缩后重新注入关键文件；
- 服务端拒绝时按完整轮次移除旧内容；
- 单条过大时保留头尾；
- 恢复次数有上限。

### 问题七：如何避免多智能体成本爆炸？

回答要点：

- 只拆分独立任务；
- 限制创建深度；
- 子智能体不能递归委派；
- 共享模型并发和速率预算；
- 共享总时间；
- 为简单子任务选择小模型；
- 评估多智能体相对单智能体的质量增益和额外成本。

### 问题八：如何评估 Agent，而不仅是模型？

回答要点：

- 最终任务成功是第一指标；
- 同时评估行动轨迹、工具、计划、记忆和安全；
- 统计延迟、令牌、重试和人工介入；
- 使用单个成功任务成本；
- 失败轨迹进入回归集；
- 用固定版本任务集做可重复对比。

### 问题九：工具输出里有恶意指令怎么办？

回答要点：

- 工具输出属于不可信环境信息；
- 不提升为系统规则；
- 权限和沙箱不依赖模型自觉；
- 敏感路径和网络策略由确定性系统执行；
- 使用攻击集评估越权和泄露。

### 问题十：如何实现 Agent 自进化？

回答要点：

- 先记录完整轨迹；
- 建立可靠验收；
- 聚类失败原因；
- 自动生成回归样本；
- 优化工具、提示、路由和记忆；
- 收集人工偏好；
- 再进行监督或偏好训练；
- 最后才考虑在线强化学习。

### 问题十一：为什么不直接使用 LangChain 或 AutoGen？

回答要点：

- 自主实现帮助掌握底层运行逻辑；
- 当前项目需要精细控制安全、并发和模型状态；
- 并不排斥框架；
- 固定流程和生态优先时可使用 LangGraph；
- 快速角色协作时可评估 AutoGen；
- 选型依据是业务复杂度、控制力、维护成本和生态。

### 问题十二：当前项目最大问题是什么？

回答要点：

- 缺少正式业务评估平台；
- 中文长期记忆召回不足；
- 没有向量和混合检索；
- 没有精确金额成本归因；
- 本地共享状态不适合大规模分布式部署；
- 没有训练和线上反馈闭环。

## 21. 面试表达模板

### 90 秒项目介绍

> 我做的 Polaris 是一个自主实现的 Python ReAct 智能体运行系统。它的目标不是只完成一次工具调用，而是让智能体可以长期、安全、可恢复地处理真实代码任务。
>
> 主循环把模型推理、结构化工具行动和环境反馈连接起来。模型每次看到文件、命令或测试结果后重新决策，没有后续工具行动时自然结束。复杂任务可以维护动态任务清单；高风险任务可以先进入严格只读的计划模式，形成计划并经过人工批准后再执行。
>
> 工具侧包含参数检查、权限判断、敏感路径保护、沙箱、资源冲突分析和安全并发。上下文侧使用真实令牌统计触发主动压缩，并在服务端拒绝超长请求时执行有边界的多阶段恢复。
>
> 系统还支持跨会话长期记忆、一次性子智能体和带任务与消息的团队协作。所有智能体共享模型并发、请求速率和总时间，子智能体也不会获得超过父智能体的权限。
>
> 每次运行都会记录模型、工具、权限、压缩和最终结果，支持会话恢复和轨迹回放。当前最需要补强的是正式业务评估平台、中文语义记忆和精确成本归因。

### 项目最大技术难点

> 我认为最难的不是接入模型，而是保证长任务中的状态连续性和安全性。长任务会不断产生工具结果，简单截断可能破坏工具行动与结果的关系，也可能丢失刚读过的关键代码。因此我把上下文管理分为正常主动压缩和服务端拒绝后的被动恢复，并限制恢复次数。压缩后还会重新注入关键文件状态。同时，任何真实动作都要经过参数级权限和沙箱，不能只依赖模型判断。

### 权限系统介绍

> 权限判断采用确定性的分层顺序。先检查参数、管理员策略、明确拒绝、计划模式、敏感路径和网络规则，再执行工具自身的参数级判断，最后才考虑会话授权、模式、自动分类或人工批准。自动分类器不能推翻硬拒绝，无人值守模式又必须具备沙箱，因此安全边界是可解释、可审计和可测试的。

### 多智能体介绍

> 系统支持一次性子智能体和显式团队两种方式。一次性子智能体适合独立调查，使用干净上下文并只返回结论；显式团队则有共享任务、成员消息和进度状态。所有成员共享模型并发、请求速率和总时间，权限不超过父智能体。可写任务还能使用独立版本控制工作区，减少并发修改冲突。

### 评估体系介绍

> 当前项目已经具备确定性测试模型、完整运行轨迹、令牌、时间、轮数和工具统计，但这些属于评估基础设施，还不是正式业务评估平台。下一步我会建立版本化任务集和自动验收，统一统计任务成功率、端到端延迟、单个成功任务成本和安全指标，并把失败轨迹自动沉淀成回归样本。

## 22. 面试前速记清单

### 必须能讲清的主流程

用户请求  
→ 上下文和记忆  
→ 模型决策  
→ 工具行动  
→ 权限与沙箱  
→ 工具执行  
→ 环境结果  
→ 重新决策  
→ 最终答案  
→ 日志、会话和记忆

### 必须能讲清的三个决策层

- 模型决定下一步做什么；
- 运行时决定怎样调度和恢复；
- 安全系统决定是否允许执行。

### 必须能讲清的三个规划层

- 动态任务清单；
- 显式计划和人工批准；
- 多智能体任务拆分。

### 必须能讲清的三类记忆

- 当前任务短期状态；
- 可恢复会话记录；
- 跨会话长期语义记忆。

### 必须能讲清的四类评估

- 效果；
- 效率；
- 成本；
- 安全和鲁棒性。

### 必须主动说明的项目边界

- 没有使用 PyTorch；
- 没有使用 LangChain；
- 没有使用 AutoGen；
- 没有强化学习训练闭环；
- CoT 能力主要来自底层模型；
- Plan-and-Execute 是工程化变体；
- 长期记忆目前主要是词法检索；
- 中文记忆召回存在不足；
- 正式业务评估平台尚未完成。

### 最后一句

> 这个项目的核心价值，是把不确定的大模型决策放进一个有状态、有工具、有安全边界、有恢复能力、有运行数据的确定性系统中；下一步则是通过正式评估和真实业务反馈，让这个系统持续优化并形成产品闭环。
